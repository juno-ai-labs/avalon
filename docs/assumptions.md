# Assumptions

These choices resolve low-level ambiguity without changing the product contract.

1. One Google-authenticated Rally account may hold several explicit workspace memberships across configured deployments. The desktop selects one workspace at a time and never merges their content; each workspace keeps one immutable region.
2. configured deployments deployments run identical code with separate bindings. Local development starts both emulated regional Workers so cross-region discovery and switching exercise the real boundary, and uses a header-gated development identity only when `RALLY_DEV_AUTH=true`.
3. The Hono API is the only public application backend. Electron loads a bundled renderer and never loads an arbitrary hosted page into its privileged window.
4. UUIDv7 identifiers are generated at the service boundary for sortable uniqueness.
5. Each conversation's `AgentLoopDO` (still bound as `SUBSTREAM_AGENTS`) stores its ordered short text parts, runs, and receipts in local SQLite. WorkspaceDO owns workspace-scoped product state, each Canvas's and Sidekick's parent metadata (see [hosted conversation parents](hosted-conversation-parents.md)), and cross-conversation queries. Regional D1 is limited to identity, membership, routing, migration/control, and operational audit/telemetry; it stores no product serving projection. R2 stores uploads, large connector payloads, and snapshots.
6. OpenRouter model names are configuration, with conservative defaults documented in `.env.example`, and are chosen by the `agent-model-*` flags rather than by anyone using the product. The one exception is the composer's model control described in item 19, which is a developer-mode affordance rather than product UI: with Debug enabled off — every ordinary installation — there is still no model selector anywhere in Rally.
7. Google APIs are implemented directly over their documented REST endpoints so connector behavior remains Worker-compatible and the dependency surface stays small.
8. A development seed is explicit and test-only. Production startup never creates demo records and the desktop does not silently fall back to hardcoded data.
9. The supplied screenshots define density, proportions, typography, color, transcript alignment, run-history treatment, and right-rail behavior. Their product-specific labels are examples, not data to hardcode into production.
10. There is no background-task panel: what the harness did belongs to the transcript, which already carries every tool event in the order it happened, and a second list of the same events beside it was one place too many to read the same run. Background-task cards were retired with the panel that held them, and a transcript link that focused an event has nothing left to focus from. The right rail's sections are Participants, Resources and Details; where it opens and how wide it is are item 16.
11. The provided `.env.local` remains untracked. Existing keys are preserved. Missing provider credentials produce explicit setup errors while their complete integration paths remain testable with fixtures.
12. Cloudflare resource creation/deployment is attempted only after local verification and only when the supplied account credentials satisfy Wrangler authentication. No existing named resource is deleted or replaced.
13. “Packageable Electron application” means a reproducible platform build configuration and successful unpacked packaging on the current host; code-signing/notarization credentials are outside the prototype prerequisites.
14. Application → Developer → **Debug enabled** is a per-device preference stored beside Lockdown mode in `application-settings.json`, not workspace state, because it describes how this installation behaves rather than what the workspace is. The *section* it sits in is not per-device: it is offered only where the service's `developer-settings` flag says so, and what the renderer reads is the stored preference **and** that flag, so a stored `true` is inert while the flag is off and comes back intact when it returns — see [`feature-flags.md`](feature-flags.md). Everything below therefore describes the preference as it is in effect, never as it is stored. It decides how much of the right rail's **Details** section is shown: with debugging off it carries only the rows that describe the conversation to a person — Email where it has an address, then Created by, Created, and Last activity — and everything that describes how it is wired (the latest harness run's status, origin, model and times, and the conversation's ID with its copy control) appears only when debugging is on. The address itself is clipped to one line in both states, because it is a value people copy rather than read; the preference decides which rows exist, never how one of them is laid out.
15. The transcript reads as people on one side and Rally on the other: every person-authored turn sits on the right — the signed-in person's, a coworker's, and one relayed in by a connector on someone's behalf — while Rally keeps the full-width left column. Who sent it is carried by the header above the bubble (accent dot, name, and for a relayed turn its source), never by which side it is on, so a turn does not change position when the person who wrote it is not the person reading. This refines item 9: where a supplied screenshot shows a coworker's turn on the left, the rule above wins.
16. The right sidebar architecture remains in code, but the shell host, open controls, width reservation, and native-window expansion are disabled. Explicit artifact and attachment clicks open the conversation's right panel; resource management reuses inspector content there. Arriving embeds open nothing. Route changes close previews. The retained frame opens at an even split with the conversation ([`desktop-layout.md`](desktop-layout.md)) and otherwise defaults to 320px, with a 280px minimum and viewport-derived maximum shared with its resize handle, and a double-click on that handle, or `Enter` while it holds focus, restores the 320px default rather than collapsing the frame, which has a close control of its own. The restore runs through the same clamp the drag does, so on a window whose derived maximum is under 320px it gives that maximum instead: the reset is to the widest the frame is currently allowed, not to a number the drag itself could not reach. The key is not a convenience: the handle's arrows step by a fixed amount, so it is the only keyboard route to that width.
17. The `system_kind` column on a conversation's identity survives the retired digest, whose scheduled runs each executed in a conversation marked `system_kind = 'digest'` rather than in no conversation at all, because the agent loop is conversation-shaped end to end. Every current producer — Canvas creation, Sidekick runs, agent communication — writes `null`, and the rows the digest made remain unreaped. Visibility is a separate column: `scope` says who may read a conversation, in the same `personal`/`workspace` vocabulary `notes.scope` uses, and is enforced from the row rather than inferred from `system_kind`.
18. Where a sidebar overlays the screen rather than sitting beside it, it still never covers the header controls that open it: those move left to sit beside the panel. A panel that is on its way out is laid out for as long as it is on screen — the room it occupies is not reclaimed, and the slot is not re-targeted at a width nothing is about to show, until its fade is over.
19. The composer's model control appears only while Application → Developer → **Debug enabled** is on. On an existing conversation it is settled: its trigger is disabled and it names the latest run's model, or the pin where that run recorded none, because a pin is written once when the conversation is created and changing it mid-transcript would leave a run reading a context its own earlier turns were written into by a different model. The control also has a choosable shape that pins the conversation ahead of the `agent-model-workstream` flag, where choosing nothing sends nothing and unpinned is labelled **Default** rather than named after a model, because which model it resolves to is the flag's answer and the renderer cannot see the served variation; no composer currently offers it (`ComposerModelControl` in `apps/desktop/src/renderer/components/composer-input.tsx`). A pin covers the conversation's agent alone; the inline subagent and Sidekick architect keep their own flags.
20. A system row in the transcript is clamped to five lines with the rest behind a control, and every system row is treated the same way regardless of what wrote it. Nothing on the wire separates a one-sentence note from an entire run prompt: six call sites write the same `('system','system')` shape, and a discriminator threaded through the serializer would be one more field each of them has to keep true, with a new producer defaulting to getting it wrong. The rendered height is the only signal that cannot go stale, so the control appears only where the clamp is actually hiding something and a short note is untouched. Five is a judgement rather than a measurement — enough to tell an inbound email's sender and subject from a run prompt's opening instruction, short enough that several in a row still read as notes beside the conversation rather than as part of it — and it is one number, `--system-message-lines`. The row keeps the newlines it was written with, because a line count is only a useful measure of a message whose lines are its own: collapsed, an inbound email's warning, sender, and subject ran onto two wrapped lines, which never reached the clamp at all. The open state is bounded too, at 320px with its own scroll, so opening the largest prompt cannot restore the wall of text the clamp exists to remove.
21. A timezone somebody chose in settings outranks the one their machine reports, and an account that has never chosen keeps following the machine. Both halves are one column, `users.timezone_source`: while the source is `client`, a desktop sign-in and the desktop and browser clients' device reports (at launch and on focus) set the account from `Intl.DateTimeFormat().resolvedOptions().timeZone`, and they stop the first time somebody fixes a zone in Account → Default timezone; turning on Set timezone automatically resumes following. The alternative — the machine always winning, which is what the sign-in exchange used to do — makes the settings control a suggestion that survives until the next sign-in from another zone, and moves every Sidekick the person scheduled without telling them. Following the machine forever would also be defensible for somebody who never opens settings, which is exactly the case that keeps working. The consequence to accept is the reverse one: after a deliberate choice, moving city means changing the setting, because Avalon can no longer tell a person who travelled from a person who wanted New York hours while sitting in London — and only one of those two readings is recoverable by the person noticing.
22. While an IME composition is in flight, every composer, dialog, and text field in Rally defers to the IME rather than acting on the keystroke itself. Between `compositionstart` and `compositionend` the input method owns the keyboard: `Enter` commits the candidate under the highlight, `Escape` abandons the composition, and `Tab`, the digits, and the arrows walk the candidate window. Acting on any of them sends half-composed text, runs a command nobody chose, or destroys a draft with no undo. The visible consequence, and the product contract, is that a Korean (2-Set) or Japanese writer presses `Enter` twice to send a message — once to commit the conversion, once to send — and that is deliberate rather than a bug to report: it is what Slack, GitHub, and VS Code all do, and a writer who has used any of them will expect it. Where the surface is a `ComposerInput`, the suppression lives in that one component and its hosts never see the keys at all; a plain field — the onboarding organization name, the header's inline rename editor, the Radix dialog's own Escape — carries its own copy. A window that closes on `Escape` carries it too, in `renderer/lib/window-escape.ts`: the keystroke that abandons a candidate must not take the window and the sentence in it. The signal is `KeyboardEvent.isComposing`, which the DOM sets on every key dispatched during a composition, chords included; `keyCode === 229` is kept beside it as the legacy composition signal, for the IME and platform paths that deliver a composition keydown with `isComposing` unset. Both are read off the event rather than from React composition state, because `compositionend` and the committing keydown have no guaranteed order. The one predicate is `apps/desktop/src/renderer/lib/ime.ts`, and it carries the reasoning.
23. Any scroller that reaches one viewport of content in ordinary use reserves its scrollbar gutter up front, with `scrollbar-gutter: stable`. Rally styles `::-webkit-scrollbar` globally at 9px, which opts every scroller out of Chromium's overlay scrollbars and into classic space-consuming ones, so a scrollbar that arrives mid-session takes those 9px out of the content box — shifting a centred column sideways by half of them, re-wrapping the text beside it, and re-truncating a fixed-width list's rows. Reserving the space costs the same 9px permanently and changes nothing when the scrollbar appears, which is the trade: a gutter nobody notices in a pane that never scrolls, against a jump under the reader's eye in one that does. "Reaches one viewport in ordinary use" is a judgement made per scroller rather than a measurement, and no automated test records those judgements: a scroller that qualifies carries `scrollbar-gutter: stable` at its own rule, one left out carries a comment there saying why, and the result is verified in a real window. The composers are the standing exception, and reserve their gutter with `overflow-y: scroll` instead: the highlight layer behind a composer's textarea has to agree with it about where every line wraps, that pair was proved against the older property, and swapping mechanisms would mean re-proving it for no visible gain.
24. Whatever holds the top-left of the main window also holds the window's own buttons clear of anything readable. Ordinarily that is the navigation sidebar, whose 48px title bar exists for no other reason; below 921px the sidebar leaves the flow for a drawer and the Canvas and Sidekick headers inherit the job, starting after the buttons rather than under them — and the control that reopens the drawer keeps its whole hit target while the title truncates, being the only way back to the navigation at that width. This refines item 18: a header does not merely stay clear of the panels that overlay it, it stays clear of the platform's chrome too. How far the buttons reach is `--window-controls-inset`, `0` by default and raised only by `.workspace-shell.has-overlay-window-controls`, added from `runtime.platform`: the main window asks `hiddenInset` of macOS, which paints its traffic lights over the page, and `hidden` of everything else, where the buttons end up in the window manager's own frame or are not drawn at all. An unconditional gutter would have been one line and no runtime dependency, and was rejected — it indents a header on two platforms against buttons that are not there, at exactly the width where room is scarcest. The value, 82px, clears the traffic lights at their widest (macOS 26: three 14px buttons on a 23px pitch from `trafficLightPosition` x: 8, ending at 68) with 14px of air; `.meeting-titlebar` reserves the same band and reaches it independently, as a flat 82px on every platform, because that window renders no `.workspace-shell` and so has no class to be told the platform by — wiring it to this property would zero its gutter rather than share one. The name sits outside the `--av-` namespace on purpose: a theme has no opinion about window chrome, and the design-token registry does not declare it. Nothing outside macOS can prove any of this — a Linux sandbox has no traffic lights to be covered by — so the check is a manual one in [`e2e.md`](e2e.md).
25. **Resolved 2026-09-13, against a live account — recorded because the guess was wrong in a way worth remembering.** This entry used to argue that Fireflies' `TranscriptsQueryScope` enum was spelled in lower case, reasoning from its documentation's option list over a conflicting sentence above it. The casing judgement was right and the premise was not: **there is no such type**. Introspecting `Query.transcripts` gives `scope: String`, and declaring the documented type name failed *every* search with `GRAPHQL_VALIDATION_FAILED` — including searches that sent no scope at all, because an unknown type in the variable declaration invalidates the document whether or not the variable is used. The same introspection showed `participants: [String!]`, which the checked-in `[String]` was also rejected against. Both are fixed, and the accepted values are now quoted from the provider's own constraint message rather than inferred: *"scope must be one of the following values: title, sentences, all"*, alongside *"keyword is required when scope is provided"*. The lesson is the general one: a documented type name is not evidence that the type exists, and a schema is cheap to ask. `packages/connectors/src/fireflies-live.test.ts` is what asks it.
