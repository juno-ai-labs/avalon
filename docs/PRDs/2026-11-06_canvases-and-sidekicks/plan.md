> Companion to [prd.md](prd.md). Written 2026-11-06 from a read-only survey of
> the tree. The product owner's answers to the PRD's open questions are in the
> PRD's decision log; this plan is written against them.

The two modes already exist in the codebase and are being pulled to the front.
The survey confirms that for Sidekicks almost entirely, and for Canvases in
every part except live co-editing by people, which the product owner has
removed from scope (see the decision log). The pivot is therefore mostly
deletion plus wiring, with no new subsystem.

## 2. Decisions this plan is built on

Recorded in the PRD's decision log on 2026-11-06. In short:

- Existing Threads, Breakouts and Channels are deleted at cutover through the workspace-retirement walk.
- A Canvas has its own participant list; default is creator-only; an organization-wide option exists; guests can be invited.
- Anyone a Sidekick is shared with can talk to it. Delegate access is used only for runs its triggers start or that a delegate asks for; a non-delegate's request runs under the requester's own access, and a tool that would need a delegate is refused with a reason.
- Editing stays as it is: Rally republishes; people comment. Live co-editing, cursors, selections and the pending-edit shimmer are out of scope.
- Presence in a Canvas stays: who is in a Canvas now shows in the sidebar row, the home page's Live now group and the header face pile.
- No feature flag; one cutover train.
- Slack mentions and inbound email stop creating conversations. Slack and email stay as Sidekick triggers and delivery, with run-child bindings kept.
- Suggested Work, routing suggestions, digests and the browser session import are deleted. Push stays for Canvas Chat mentions, "Needs input" and finished runs.
- Sideline is deleted; its destination model is Threads.
- All iOS code is deleted.
- Help center and site copy change in the same train.
- A Canvas is any generated artifact, not only a live site: documents, spreadsheets, images, PDFs, archives and sites.
- A Canvas is identified by its conversation, not by an artifact or resource, so one Canvas conversation can generate many artifacts. A new Canvas starts with no artifacts.
- An open Canvas reuses today's conversation layout: the conversation in the main pane, the artifact in the right panel once it is ready. The mockup's artifact-first pane with Chat and Comments tabs is superseded.
- The Sidekick's shared conversation keeps the wizard and run separation: managers edit through the wizard, a message addressed to the Sidekick starts a run, and runs appear as rows. A Slack mention of Rally no longer creates anything.
- Canvas conversations stay in the existing conversation Durable Object, which is renamed; no new Durable Object and one hosting primitive in WorkspaceDO for Canvases and Sidekicks.
- Every Thread and Breakout transcript is dumped to R2 as text before it is retired.
- Thread-scoped Sidekicks convert to organization scope.

## 3. Target shape

Two conversation parent kinds remain, both hosted inside WorkspaceDO the way
Sidekicks already are: `automation` (the Sidekick; the wire name stays, per the
storage-name rule in `AGENTS.md`) and `canvas` (new). Every conversation stays
a `SubstreamAgent`; the engine, transcript, loops, tools, compaction, memory
copies, feed socket and composer are untouched.

- **Sidekick** = `automation_directory` row + shared conversation `"0"` + run children. The directory row gains a share list and a per-viewer unread cursor for `"0"`.
- **Canvas** = a conversation first. Its id is the conversation coordinate (the parent id of its `canvas`-kind conversation, today's `WorkstreamId` brand; substream `"0"` is the Chat), and the artifacts it generates hang off it through the existing `generated` resource link, one today and possibly several later. The Canvas, not a Thread, is each artifact's owner and audience. Comments are annotations in the conversation, as today.
- **Sidebar** = one `WorkspaceSidebarSchema` with `canvases`, `sidekicks`, pins, unread, presence. The Channel, Thread, Space, Activity, channel-rail and conversation-view topics go.

## 4. Phases

Each phase is a train of reviewable PRs. Line counts come from the survey.

### Phase A: groundwork, no user-visible change

Server, Sidekicks.

- A-1. The shared conversation keeps the wizard and run separation. Substream `"0"` under an automation stays the Sidekick's own conversation, read by everyone the Sidekick is shared with. A message there addressed to the Sidekick starts a run under the Sidekick's definition, the same path a manual trigger takes, with the message as the opening; the run answers in its child conversation and its row in `"0"` carries the reply. That holds for managers too. A manager edits the Sidekick by marking a message as a wizard edit with an explicit intent on the message (`intent: "edit_sidekick"`), which the server accepts only from a manager and routes to the wizard; without it, a manager's message routes like anyone else's. `classifyAddressing` decides whether a message is for the Sidekick or for the other people. `rally:sidekicks` authoring tools load only for a wizard turn (`services/integrations.ts`, `packages/agent-harness/src/automation-creator-tools.ts`).
- A-2. Run rows in the shared transcript: `HostedSidekick` writes a collapsed run row into `"0"` when a run is provisioned and updates it as the run's state changes and when its reply lands (reuse the `automation_activation` message type with `runId`, status, step count and the reply). The row is a projection of `sidekick_runs`, which stays authoritative; a replay rebuilds rows from that table so the two cannot drift. `sidekick_runs_read` backs expansion.
- A-3. `conversation_post` default target becomes the Sidekick's `"0"`; `SubstreamAgent.appendConversationPost` admits `parentKind: "automation"` and `canvas`; the `sidekick_conversation_attachments` CHECK admits `canvas` and drops `workstream`. Landed on 2026-11-06 admitting `automation` only: `canvas` admission and the CHECK change are owed to step A-7, and the `workstream` value stays in the CHECK until phase C removes Thread attachments.
- A-4. Audience: `HostedSidekick.authorizeViewer` reads a share list (`personal`, `workspace`, or explicit people). Remove `homeAdmits`, `sidekickGrantViewer` and the owner rule at `services/authorization-service.ts:256`. Unread for `"0"` is the conversation's existing read state (`member_attention`, `acknowledgeRead`, `markUnread`); nothing new is stored. "Needs input" = existing `conversationNeedsViewer` or `delegationAttention`. Delegation per the decision log: a run started by a non-delegate's message runs under the requester's own principal, and a tool that needs a delegate refuses with a named reason. Landed on 2026-11-07 with the audience rule, the `people` share list (migration 136, a separate `audience` field beside `scope` so installed desktops keep parsing), `POST /automations/:id/audience`, unread and needs-input on the sidebar row, and one new table, `sidekick_viewer_reads`, projecting each reader's read state of "0" so the sidebar row costs no round trip; the non-delegate-runs-under-own-access rule landed the same day (`sidekick_runs.requester_user_id`, migration 138), for guests on the share list as much as members.
- A-5. Remove the `workstream` Sidekick scope, the `owning_workstream_id` cascades, Channel-rail bumps, Thread-attached and recommended Sidekicks and `GET /automations/workstream/:id`. A WorkspaceDO migration converts `workstream`-scoped Sidekicks to `workspace` scope.

Server, Canvases.

- A-6. Canvas identity: a Canvas is created as a `canvas`-kind conversation, and its id is that conversation's parent id, so one Canvas conversation can generate many artifacts. A WorkspaceDO migration adds `canvas_directory` (canvas id, title, created by, updated at, last editor, writer Sidekick id, visibility `creator | participants | workspace`) and `canvas_participants` (built on the scope-grant and invitation tables re-keyed to a Canvas, so guests can be invited the way they are today). Artifacts stay resources linked to the conversation by the existing `generated` relationship in `workstream_resource_links_v`, and each keeps its own version history. `artifact_registry.workstream_id` and `artifact_state.workstream_id` now hold the Canvas id, which is the conversation id, so no column changes meaning. Only the creator and the Organization's owners and administrators change a Canvas's audience (decision log, 2026-11-07).
- A-7. `canvas` parent kind on one hosting primitive: generalize `HostedSidekick` into a hosted conversation (participants, share list, artifacts, pins, unread, children) that a Sidekick extends with its definition, triggers and runs, rather than cloning it into a second host. `ConversationParentKindSchema` gains `canvas`; `SocketService.resolveHostedParent` and the ticket `pk` learn it. `ArtifactOpenService` admission moves from "attached to an accessible conversation" to "Canvas participant or organization-wide Canvas". No new Durable Object: a Canvas conversation is a `SubstreamAgent` like every other conversation. Landed on 2026-11-07 as `HostedConversation`, which `HostedSidekick` and `HostedCanvas` extend; `createCanvas` (the directory row and the Chat with its creator seated) landed here, ahead of A-9.
- A-7b. Rename the `SubstreamAgent` class to `AgentLoopDO` with a `renamed_classes` migration tag (precedent: tag v3 renamed `WorkstreamRoom` to `SubstreamAgent`). Objects keep their storage. The same change updates `REPORTING_CLASSES`, the migration tracker's registry and dispatcher, the `SUBSTREAM_AGENTS` binding name, the eslint rule that names it, and `scripts/force-substream-agent-migrations.mjs`. - A-9. Create a Canvas: `POST /canvases` creates the directory row and the `canvas` conversation, with no artifacts yet; the client shows the PRD's empty state. The "Start from a prompt" card creates a Canvas and sends the prompt to its Chat. A Canvas a Sidekick creates starts out shared with the people the Sidekick is shared with (decision log, 2026-11-07).
- A-10. Presence in a Canvas is tracked and shown. It needs no new wire field: a Canvas id is a conversation id, so `set_presence.foregroundWorkstreamId` already carries it and `workspace_presence` already fans out per conversation. The Canvas sidebar row (green dot and names), the home page's Live now group and the header face pile read it.
- A-11. Rally in a Canvas Chat: a system-prompt variant with the Canvas's current files as context and `publish_resource` scoped to the Canvas. Each republish is a version attributed to Rally in the Canvas's history.

Client, built as routes the rail does not yet show.
