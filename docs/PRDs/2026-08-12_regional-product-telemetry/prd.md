# Regional product telemetry and crash reporting

> Created: 2026-08-12
>
> Scope: Avalon desktop, regional APIs, product analytics, error reporting, and a future public-site source
>
> Companion documents: [research](research.md), [design](design.md), [state](state.md)
>
> Standing brief: [Avalon implementation brief](../2026-08-05_avalon-implementation-brief/prd.md)

## Summary

Avalon needs a privacy-bounded telemetry system that explains how people use the product, connects desktop activity to regional API outcomes, and makes Electron failures diagnosable. The product cannot obtain those capabilities by placing a general-purpose analytics SDK in the renderer: Avalon handles unusually sensitive work content, the renderer is deliberately isolated, and every authenticated workspace is pinned to either the Global or EU service architecture.

Avalon therefore owns a small, vendor-neutral event and crash-reporting layer. The Electron main process is the desktop telemetry authority. It accepts only typed, allowlisted signals from the renderer and preload, adds safe application context, stores a bounded local delivery spool, and sends batches to an Avalon collection boundary. Workspace-bound activity uses the authenticated regional API; logged-out onboarding uses a narrow, capability-bound Global bootstrap endpoint. Before an explicit region exists, that edge reduces Cloudflare's request geolocation to a coarse provisional route: an affirmative EU-country request goes immediately to the EU internal sink through named RPC; non-EU, unknown, and failed geolocation requests go immediately to the Global pipeline and PostHog. Avalon stores neither the source IP nor detailed geolocation and has no region-pending event holding area. A later explicit region applies prospectively and does not migrate or duplicate earlier onboarding events. Regional API code emits server-side signals through the same contract.

Native crashes use a separate path. Electron Crashpad writes minidumps to a route-final local database without placing a credential in its submission URL. On the next launch, before Crashpad starts, Avalon rotates the inactive database into a bounded upload spool; main then sends eligible reports to their capture region with header-based authentication. This intentionally trades immediate fatal upload for a defensible credential boundary. The crash pipeline stores received dumps separately for 90 days and symbolicates them using private release artifacts. In Global, PostHog receives the complete sanitized, symbolicated structured crash report and provides the engineering issue workflow. In EU, the equivalent full structured report and its issue workflow remain inside Avalon's isolated regional platform. Raw minidumps, source maps, symbols, memory fragments, unsanitized frames, and source excerpts never go to PostHog. PostHog is not the raw crash archive or the source of truth for consent, residency, event schemas, or internal delivery state.

The default collection model is intentionally hybrid. Avalon automatically captures a narrow set of content-free lifecycle and reliability signals. Product teams add explicit semantic events for meaningful actions and outcomes. Avalon does not enable DOM autocapture, generic click or key capture, session replay, console capture, arbitrary network breadcrumbs, or an unrestricted `capture(name, properties)` API.

Essential content-free reliability telemetry, low-data product analytics, and detailed crash reporting are enabled by default. Each user has a Product analytics setting that defaults on. Turning it off stops that user's semantic product analytics and every detailed diagnostic payload, including JavaScript exception stacks, diagnostic breadcrumbs, and native crash dumps. Essential content-free reliability counters continue so Avalon can operate and secure the service, but they contain no message, stack, fingerprint, or breadcrumb. Native upload is disabled immediately; preventing new local Crashpad dumps and safely purging its database takes effect on restart because Electron Crashpad cannot be stopped once started. The settings UI has no narrower crash-only switch: Product analytics is the single user-facing control for nonessential telemetry.

## Motivation

This is a product-directed measurement and reliability capability, not a response to a quantified incident or support trend. The 2026-08-12 product request explicitly requires PostHog integration, regional behavior, deep Electron crash reporting, privacy-aware automatic capture, and client/server signal correlation. No support-frequency or production-crash baseline was supplied, so this PRD does not invent one. The verifiable source baseline explains why the work must precede any trustworthy measurement:

- The [desktop main process](../../../apps/desktop/src/main/index.ts) has two production failure observers—renderer termination and unresponsiveness—and both end in local logging. The [renderer error boundary](../../../apps/desktop/src/renderer/App.tsx) also ends in local logging. The repository contains zero production remote desktop crash-report transports, so 100% of failures observed by these hooks are unavailable for remote grouping, affected-session counts, or release comparison unless a user separately supplies local evidence.
- The [desktop build configuration](../../../apps/desktop/electron.vite.config.ts) generates source maps for all three JavaScript bundles—main, preload, and renderer—but the repository has zero private artifact-upload or production symbolication paths. All three production bundle classes therefore lack a remote symbolication lifecycle.
- The regional APIs have structured logs and deliberately content-free root-run Analytics Engine rows, but the repository has zero product-analytics destination adapters and zero shared client-intent/server-outcome analytics contracts. Activation-funnel coverage and crash-free release baselines are consequently both zero today; continuing without this work cannot establish the frequency it is meant to measure.
- The [public Cookie & Tracking Notice](../../../apps/site/cookies/index.html) explicitly promises zero behavioral analytics and no nonessential consent banner. Any future site measurement has a concrete disclosure cost and cannot be introduced incidentally with desktop telemetry.

Leaving this unchanged means every future desktop crash still requires reproduction or user-supplied local evidence, every release still lacks a crash-free comparison, and product changes still lack an authoritative activation funnel. The initial rollout therefore establishes the measurement baseline itself; later investment decisions must use observed volume, loss, support value, and funnel coverage rather than retroactively treating this PRD as evidence of customer demand.

The design is informed by current official documentation for PostHog, Twilio Segment, Sentry, Electron Crashpad, OpenTelemetry, Amplitude, RudderStack, Snowplow, Bugsnag, and Honeycomb. The detailed comparison and links live in [research.md](research.md).

## Goals

1. Give product and engineering a trustworthy view of activation, adoption, retention, funnel completion, and release health without collecting customer content.
2. Detect and diagnose handled JavaScript errors, unhandled exceptions and rejections, renderer failures, hangs, unclean exits, and native Electron crashes across supported desktop releases.
3. Preserve Avalon's Global/EU boundary from collection through temporary storage, durable delivery, crash storage, symbolication, destination selection, deletion, and support access.
4. Join client intent to server truth with stable event, session, operation, request, and trace identifiers while making duplicate delivery and clock skew explicit.
5. Make event collection governed and testable through versioned schemas, a tracking plan in source control, field-level privacy classifications, and destination-specific transforms.
6. Keep collection resilient and non-blocking through bounded local buffering, regional durable outboxes, retry with backoff, idempotent delivery, and observable dead-letter handling.
7. Keep PostHog replaceable. Avalon owns consent, identity derivation, the accepted event contract, delivery state, raw native dumps, deletion workflows, and destination routing.
8. Establish a safe extension point for future public-site analytics without changing the site's current tracking posture in the first release.

## Non-goals

1. Recreate Segment's full customer data platform, identity graph, audience builder, or catalog of hundreds of destinations. **Deferred:** one external destination does not justify another processor or a general CDP; the adapter boundary keeps that option open if destination count grows.
2. Recreate Sentry's full issue-management UI, source-control integration, performance tracing product, or support workflow inside Avalon. **Deferred:** the first scope needs regional crash intake and a minimal EU issue surface; the native-crash spike may still select a dedicated crash product if custom issue handling is not economical.
3. Record prompts, model responses, transcripts, files, connector content, emails, note bodies, terminal output, arbitrary logs, or other customer content for analytics or crash context. **Rejected:** these categories are unnecessary for the stated product questions and would defeat the privacy boundary.
4. Enable Electron renderer DOM autocapture, generic click or keyboard capture, session replay, automatic console breadcrumbs, or automatic request/response capture. **Rejected:** these mechanisms can collect customer content before a semantic allowlist can distinguish it.
5. Replace Cloudflare logs, traces, or the existing content-free Analytics Engine dataset used for service operations. **Rejected:** operational observability and product telemetry have different identity, residency, retention, and query contracts and must remain separate.
6. Use PostHog feature flags as Avalon's runtime flag system. **Rejected for this scope:** Flagship remains authoritative so telemetry delivery cannot change runtime behavior; experiments may export exposure metadata to PostHog.
7. Guarantee exactly-once analytics delivery. **Rejected:** distributed offline delivery cannot make that promise reliably; the product provides at-least-once delivery with deterministic event identifiers and destination deduplication where supported.
8. Add public-site behavioral analytics, cross-site attribution, advertising pixels, or a consent banner in the first release. **Partly deferred and partly rejected:** aggregate cookieless site measurement is deferred to its own notice/consent gate, while durable cross-site or site-to-desktop attribution and advertising pixels are rejected by the approved scope.
9. Expose raw native crash dumps, raw stack frames, or sensitive diagnostic attachments in PostHog. **Rejected:** PostHog receives only the approved structured report; raw artifacts remain in restricted regional Avalon storage because they can contain customer content.
10. Treat telemetry as a prerequisite for completing a user action. **Rejected:** collection and forwarding failures must never change the action result, because analytics availability is not part of the product transaction.

## Product behavior

### Collection model

Every signal belongs to one of three policy classes:

| Class | Examples | Approved default | Data ceiling |
| --- | --- | --- | --- |
| Essential reliability | launch/session counters, app version, update result, process-gone reason, API outcome class, dropped-event counts | On | Content-free enums, booleans, bounded durations, opaque IDs |
| Product analytics | named screen views, explicit feature actions, funnel steps, coarse configuration choices, server-confirmed outcomes | On, with a per-user setting to disable | Allowlisted semantic properties; no customer content |
| Detailed diagnostics | native minidump, sanitized exception stack, typed breadcrumb ring | On only while Product analytics is enabled; every detailed payload stops when it is disabled | Minimum diagnostic payload, separate retention and access |

The Product analytics preference is account-scoped rather than installation-scoped. The Global identity control plane stores the canonical boolean and monotonic version as minimal account metadata, not telemetry. The active regional API receives and stores a local projection through a narrow named RPC so API-native and asynchronous events can enforce the same choice without querying another region on an event path. Region activation includes the current preference version. This control RPC carries a Global-issued opaque `preference_subject_handle`, the preference, and the version. The handle is random, region-bound control-plane metadata mapped to the regional user during activation; it is never an analytics identity, event property, destination field, or general account credential. The RPC never carries an event, dump, stack, raw platform identifier, or workspace content. Existing users' stored choices apply as soon as the identity bootstrap session is established. New users use the approved default-on value. The control remains in the normal authenticated Settings experience; Avalon does not add a Product analytics toggle or consent interruption to onboarding.

The desktop applies an opt-out locally before making a network request, stores it durably, stops product events and detailed diagnostics, stops and purges the separate crash-upload spool, invalidates the active Crashpad generation, and queues the preference mutation separately from telemetry. Nonessential collection cannot resume until the regional API acknowledges the canonical version. The API commits the canonical preference and its regional projection before acknowledging the change. Other installations refresh the setting at session bootstrap and on a version notification; a stale write must refetch rather than overwrite a newer choice. An offline opt-out remains locally effective and is sent before any nonessential delivery after reconnect. Opt-in requires a server acknowledgement before collection resumes.

Logged-out anonymous collection uses the durable local setting; logout never resets an opt-out to the default. A fresh installation has no account preference and uses the approved default-on value. If subsequent authentication reveals that the account is already opted out, the identity boundary closes the epoch, issues no alias, suppresses further nonessential events, and deletes every attributable accepted event, sink record, derived contribution/index, correlation, and queued or replayable copy still held inside Avalon through its original route without sending the person's identity across regions. Any copy already accepted by PostHog follows separately managed provider configuration.

The regional API checks the persisted projection when a user-attributable server event is created and again before it is forwarded. An opt-out suppresses queued product events and detailed diagnostics for that user, including asynchronous outcomes created by earlier actions. If the current preference version cannot be established, the API permits only essential reliability events. A workspace owner or administrator may disable Product analytics for the entire workspace. The workspace policy defaults on, can only narrow collection, and cannot override an individual's opt-out to turn collection back on. Either opt-out disables semantic product events and detailed diagnostics for that workspace context; essential content-free reliability signals continue.

Automatic collection is limited to events whose shape is stable and whose fields are content-free:

- application launch, ready, foreground/background, graceful exit, and inferred unclean exit;
- desktop session start and end;
- update check, download, apply, and rollback outcomes;
- renderer process gone, renderer unresponsive/responsive, preload initialization failure, main-process unhandled-exception occurrence, and renderer error-boundary occurrence, expressed only as bounded content-free classes;
- API request duration and outcome class for an allowlisted operation name, without URL, query, headers, or body;
- spool pressure, rejected event counts, destination delay, and crash-upload state.

All business events are explicit. A feature emits a typed event such as `workspace_switch_completed` or `run_completed`; it does not pass an arbitrary string and property bag. Generated router instrumentation deliberately calls a named `screen_viewed` method with a registered screen enum when a planned route becomes visible. That is Product analytics subject to opt-out, not automatic DOM/URL capture. The tracking plan defines the event owner, source of truth, allowed sources, property schema, privacy class, retention, sampling, and destination mappings.

### Identity and correlation

Avalon does not send names, email addresses, workspace names, raw database identifiers, authentication tokens, IP addresses, or device-advertising identifiers to PostHog.

Established regional person, workspace, and installation analytics identifiers use versioned keyed hashes. Logged-out epochs, EU pre-workspace telemetry subjects, site sessions, and preference subjects use separate random, purpose-bound namespaces so none can be repurposed as a cross-region join key. The service records the key version or restricted handle mapping needed for deletion and controlled rotation. The lifetime installation identity is reserved for schemas that require device-level reliability measurement and is never aliased to a person. Pre-auth product activity instead uses a random anonymous epoch created for the current logged-out journey. Once authentication and an explicit workspace route establish same-region eligibility, Avalon automatically links that epoch—and only that epoch—to the derived person identity.

Identity has four explicit scopes: `installation` for device-level reliability, `anonymous-epoch` for one logged-out product journey, `platform-user` after Global identity authentication but before workspace activation, and `workspace-user` after a regional workspace session exists. The platform-user state is pseudonymous rather than anonymous: Avalon knows the canonical platform user, but no analytics destination receives the raw platform ID. A server-created `onboarding_journey_id` joins the bootstrap session's client presentation and intent events to authoritative onboarding API outcomes. It is not an authentication credential and is bound server-side to the bootstrap session. The server also binds one coarse provisional route to the journey so VPN or network changes cannot split it across destinations. Logout, explicit account switching, and abandonment of a login attempt close the current anonymous epoch before another account can authenticate against it; the next logged-out journey receives a fresh identifier.

Before authentication, main obtains a short-lived, route-bound capability for the random anonymous epoch from the Global bootstrap endpoint; that capability authorizes only generated logged-out onboarding schemas and carries no account authority. After authentication, the identity-only session authorizes the platform-user subset until a workspace exists. Both modes validate and route immediately using the server-bound provisional route. Global events enter the normal Global outbox. For an EU route, the named Worker RPC carries the exact validated projection and either the anonymous epoch identifier or a dedicated EU telemetry subject handle created by the Global identity plane for this user. That handle is opaque, EU-scoped, versioned for deletion, never used as a Global destination identity, and never exposed to the client. The EU sink uses it directly as the pseudonymous platform-user identity; it does not attempt to derive identity from an unavailable Global user row. The payload contains no raw platform identifier, Global destination identity, or geolocation field. Global retains only the minimal control mapping required for preference/deletion plus content-free delivery and deduplication metadata, not an event replay payload. Once activation, creation, or invitation acceptance establishes an explicit region, that region replaces the provisional route prospectively.

Every envelope carries a unique `event_id`. Related activity may additionally carry:

- `launch_id` for one application launch;
- `session_id` for one foreground product session;
- `operation_id` for one user-intent flow across renderer, main, and API;
- `request_id` for a regional API request;
- W3C `trace_id` and `span_id` when operational tracing exists.

`operation_id` answers product questions such as intent-to-success. Trace context answers service-timing questions. Neither substitutes for the other. The API records client-original, client-sent, server-received, and normalized event times and flags excessive clock skew rather than silently trusting desktop time.

### Client and server signals

Client and server events share one versioned envelope and one tracking plan, but each named event declares its authoritative source:

- client-only events describe presentation state or intent, such as a screen becoming visible or a user invoking an action;
- server-only events describe authoritative effects, such as a workspace mutation committing or an asynchronous run finishing;
- paired events use the same `operation_id`, such as `run_requested` from the client and `run_completed` or `run_failed` from the API;
- an event is never emitted from both sides merely to increase confidence. If two sources are meaningful, they use different names and defined semantics.

The regional API adds trusted fields such as region, environment, server release, authenticated analytics identities, entitlement tier, and outcome classification. Client-supplied values never override trusted context.

The initial onboarding plan follows the same division. The desktop owns screen presentation and explicit intent events such as `onboarding_screen_viewed`, `workspace_creation_requested`, and `invitation_acceptance_requested`. The Global coordinator owns `onboarding_state_resolved`; the regional service owns activation, creation, and invitation-acceptance completion. Events may contain fixed state and outcome enums, invitation-count buckets, and a selected-region enum after the user acts. They never contain an organization name, email, inviter name, raw invitation ID, raw workspace ID, or membership payload returned by regional discovery.

### Electron reporter

The Electron main process owns reporter initialization, policy, identity state, the breadcrumb ring, the local spool, batching, network delivery, and shutdown flush. The renderer receives only narrow preload methods generated from the tracking plan. It cannot obtain provider keys, a PostHog client, a raw destination URL, or an arbitrary event method.

The local spool contains only already-sanitized envelopes. It is bounded by count, bytes, and age; evicts the oldest low-priority analytics before essential reliability events; uses jittered exponential backoff; and reports aggregate drop counts after recovery. Logout clears authenticated identity from future events and removes queued authenticated product analytics unless retention has been explicitly approved. Crash artifacts follow a separate local lifecycle.

Developer builds provide a telemetry inspector showing the event name, schema version, policy class, allowed properties, selected region, local queue state, and validation result. Values classified as diagnostic or identifying stay redacted. This is the primary way feature authors verify instrumentation without relying on the PostHog live-event view.

### Crash and error coverage

Avalon treats crash reporting as four complementary layers:

1. **JavaScript errors.** While Product analytics is enabled, main and renderer handlers report handled failures, uncaught exceptions, unhandled promise rejections, and React error-boundary failures through a sanitized exception schema. Stack frames are normalized; query strings, local usernames, workspace paths, source excerpts, request bodies, and dynamic messages are removed or tokenized before upload. When the setting is off, only the corresponding essential occurrence class is reported, without message, stack, fingerprint, breadcrumb, or arbitrary metadata.
2. **Electron process health.** Main-process listeners report renderer termination reason, exit code class, sandbox or GPU process role, unresponsive/responsive transitions, and recovery action. Repeated events are rate-limited and grouped by launch.
3. **Unclean exits and launch crashes.** A launch marker is committed before UI initialization and cleared on graceful exit. The next launch reports an inferred unclean exit and whether the prior release was still in its launch window. This detects failures for which in-process JavaScript delivery never ran.
4. **Native crashes.** When Product analytics is enabled at launch and an explicit workspace region is already known, Electron Crashpad uses that region. Otherwise main completes a bounded coarse Cloudflare route gate before it creates the first renderer. For an affirmative EU-country route, Crashpad remains stopped: Avalon creates, retains, and uploads no pre-region native dump. For non-EU, unknown, timeout, network failure, and malformed or unavailable geolocation responses, Crashpad starts a Global-designated local database before the first renderer. There is no region-pending crash store; each database generation has a final capture route. Crashpad does not upload directly, and Avalon never reads or mutates its database while the handler is active. On the next launch, before Crashpad starts, main atomically rotates the inactive prior database and its launch sidecar into a bounded route-final upload spool, purges expired or ineligible generations, and starts a fresh database for the current route. The uploader sends eligible rotated reports with normal regional-session authentication or a short-lived main-only bootstrap capability in a header. The endpoint validates size and format, rate-limits, rechecks server-side preference or capability state where identity is known, stores the dump in regional object storage, and queues symbolication. A telemetry-region change, opt-out, or newly restrictive workspace policy invalidates the entire active capture generation before product state changes; later local dumps may still be created by Crashpad but the generation is never uploaded and is purged on restart. New eligible capture begins only after restart under the new route and policy.

Raw minidumps remain in a restricted regional crash store for 90 days from receipt and are then deleted by a verified lifecycle job. Private source maps and native symbols are uploaded by the release pipeline to the matching regional symbol store, keyed by immutable release, build, bundle, platform, architecture, and debug identifiers. Symbolication produces the complete approved structured report: scrubbed exception or crash type, mechanism and handled state, symbolicated application and system-frame summaries, stable issue fingerprint, release/build/channel, process type, platform/architecture, timestamps, derived person/installation identity where permitted, affected launch/session correlation, parser status, opaque `crash_id`, and typed breadcrumbs when the bounded crash sidecar was recovered. Every report states whether breadcrumbs are `available`, `stale`, or `unavailable`; a fatal crash can lose the newest in-memory transitions, so breadcrumbs are not guaranteed. The Global PostHog project receives this full structured report after the privacy transform. The equivalent EU report remains in Avalon's isolated EU telemetry store and is investigated through a minimal internal issue surface. Authorized support tooling retrieves the underlying raw artifact from Avalon's crash store only when policy permits; PostHog cannot retrieve it.

The crash product measures, at minimum, crash-free launches, crash-free sessions, affected installations, launch-crash rate, unresponsive-session rate, issue recurrence, first-seen/last-seen release, and release adoption. Crash-free rates use only reporting-eligible launches and sessions: detailed crash reporting must be enabled continuously from their start through their end. A setting or policy change in either direction makes the current launch/session ineligible; the next launch/session can establish the new eligibility. Essential launch/session counters still measure total usage, and dashboards show eligibility coverage alongside the crash-free rate. A crash counts once against an eligible session even if the same session produces multiple reports. Rate limiting, sampling, upload rejection, and missing consent state must not make stability dashboards silently look healthier; discarded, ineligible, and eligible denominators are exported separately.

Typed breadcrumbs are a small ring of safe state transitions—for example `screen_changed`, `update_started`, `workspace_switch_started`, and coarse API operation outcomes. They use the same schema registry, never include display text or arbitrary metadata, and are attached only when detailed diagnostics permits them. Main mirrors the bounded, already-sanitized ring to an atomic per-launch crash sidecar with restrictive permissions and a declared freshness budget. The uploader associates the sidecar by launch/process identity, deletes it with the local dump, and never uploads it separately. This makes recent context recoverable without claiming lossless capture after a fatal main-process crash.

### Regional pipeline and destinations

Each regional API exposes authenticated batch ingestion for normal events and a separately protected multipart endpoint used by Avalon's main-process crash uploader. Crashpad never places a token or capability in a submission URL. Normal ingestion validates the envelope, clamps timestamps and sizes, applies policy and redaction, derives analytics identities, and commits an accepted record to a regional D1 outbox before returning success. The Queue message contains only the region and opaque record identifier, preserving the repository's existing queue-content boundary. A regional consumer loads the record, runs destination transforms, sends it, and records attempt and terminal state.

The Global identity API additionally exposes two generated onboarding modes: a logged-out mode bound to a short-lived anonymous-epoch capability and an identity-authenticated mode accepted only while the session has no workspace. Their allowlists exclude arbitrary product events and every native dump. An existing explicit platform workspace binding supplies the route; otherwise the edge reduces Cloudflare geolocation to `eu` only when `isEUCountry` is affirmative and to `global` for non-EU, unknown, timeout, network failure, or unusable metadata. It stores only that coarse route and `routing_basis: "ip_geolocation"` or `"geolocation_fallback"` with the journey, never the IP or location fields. The handler binds the epoch or authenticated identity, applicable preference state, and journey from server state, then durably commits immediately to the Global outbox or obtains durable EU acceptance through named RPC before returning. Both routes preserve `event_id`, normalized time inputs, and opaque correlation identifiers so retries cannot double-count the funnel.

Invalid events do not enter product analytics. Production rejection records contain only fixed violation codes, a registered event/schema identifier or the sentinel `unknown`, a registered source enum or `unknown`, server-derived release/build identity, registered field identifiers or `unknown`, and aggregate counts. Unknown event names, property keys, path segments, schema strings, client release strings, and payload fragments are never persisted, logged, hashed for later inspection, or reflected to another telemetry system. Developers get local validation failures from the generated schema without echoing unsafe values. Delivery failures retry with backoff and then enter an operator-visible dead-letter state. Backlog age, rejection rate, duplicate rate, destination latency, and drop counts have explicit alerts.

The US PostHog project is the first external destination adapter and is enabled only in the Global deployment:

- use the US ingestion host only from the Global destination worker;
- set deterministic event identifiers and preserve normalized original time;
- set person-profile processing only for approved authenticated product events;
- disable geolocation and do not forward the request IP;
- map JavaScript exceptions through the supported server SDK exception API after validating its output in a privacy fixture suite;
- map complete sanitized Global native crash reports to the verified PostHog exception/error-tracking contract where supported, with an Avalon-owned typed event for approved fields that contract cannot represent;
- attach Flagship experiment exposure properties only to approved exposure and metric events;
- keep personal profiles minimal and do not send email, name, or raw Avalon IDs;
- opt Avalon data out of provider product/model development contractually or through the provider control before production data flows.

The EU deployment has no PostHog credentials, adapter route, or provider egress. Its accepted events and complete approved structured crash reports terminate in an Avalon-owned internal telemetry sink built from isolated Cloudflare primitives. Avalon prefers primitives with documented EU domicile. If a required Cloudflare primitive does not offer that guarantee, EU telemetry uses a dedicated set of bindings and datasets that is not shared with Global, and the limitation is documented. The existing shared Analytics Engine dataset is not an EU product-telemetry destination because it does not provide the required jurisdiction guarantee. A future EU-specific PostHog instance requires an explicit architecture and privacy decision before forwarding begins.

Destination configuration and credentials exist only in the matching regional server environment. A destination can be paused, sampled, replayed from the allowed retention window, or replaced without shipping a new desktop release. Destination replay preserves `event_id` and records adapter version.

### Prohibited data

Telemetry schemas and runtime redaction reject these fields regardless of consent tier unless a later PRD explicitly changes the product contract:

- prompt, response, transcript, note, document, file, email, connector, calendar, issue, chat, or terminal content;
- filenames, absolute or home-relative paths, repository remotes, branch names, window titles, URLs with path/query/fragment, DOM text, and clipboard data;
- authentication headers, cookies, tokens, OAuth material, credentials, and local secrets;
- raw request or response bodies, arbitrary console output, SQL text, and arbitrary exception metadata;
- names, emails, IP addresses, precise location, advertising IDs, raw user/workspace/database IDs, and third-party account identifiers;
- source-code excerpts and memory attachments beyond the approved minidump path.

Property names matching sensitive-key patterns are rejected. String fields have enum or strict length/character constraints. Unknown properties fail validation rather than being forwarded. Free-form user crash descriptions, if introduced later, are stored as support content under a distinct consent and retention flow and never forwarded to a product analytics destination.

### Public website

The first release does not alter the website. This is required because the current Cookie & Tracking Notice states that Avalon does not use behavioral analytics or non-essential tracking and therefore does not display a consent banner.

A later site phase uses the same public ingestion contract with a separate `site` source and separate project or dataset. Its approved scope is aggregate funnel measurement only: explicit landing-view, call-to-action, and download-conversion events use a cookieless, short-lived anonymous session identifier plus allowlisted coarse campaign and referrer buckets. The identifier does not survive the browser session and is never placed in a download, deep link, installer, Electron launch, login, or account record. Site and desktop metrics may be compared only as aggregate cohorts; Avalon creates no durable visitor-to-desktop identity or event-level join.

The site phase does not enable DOM autocapture, session replay, advertising pixels, or unrestricted client capture. Its collection edge reduces Cloudflare location to the same coarse routing outcome: an affirmative EU-country result reaches only the EU internal sink, while non-EU and unavailable results use Global/PostHog; no IP or detailed location becomes an event property or stored routing record. Before launch, Avalon updates the Cookie & Tracking Notice and subprocessor disclosures, honors Global Privacy Control, establishes any legally required consent behavior, and verifies bot filtering. Legal or privacy review may narrow this approved scope but cannot silently expand it to durable attribution.

### Retention, deletion, and access

Every schema declares a retention class. The approved product ceilings, subject to legal or privacy review requiring a shorter period, are:

- local normal-event spool: delivery eligibility ends 14 days after creation; a running app purges on deadline and a dormant app purges expired rows on the next launch before delivery;
- local Crashpad reports, manifests, invalidation records, and crash sidecars: upload eligibility ends 14 days after creation; a running app purges the rotated upload spool on deadline, and all expired rotated or unrotated material on a dormant device is physically purged on the next application launch before any upload attempt or Crashpad restart;
- regional accepted-event outbox, replay payload, terminal-failure state, onboarding route, and delivery/deduplication receipt: 90 days from regional acceptance or metadata creation; delivery-state changes never restart the clock;
- rejection metadata: rolling 90 days, stored in independently expiring time buckets so a new rejection cannot renew an earlier observation;
- raw native dumps: 90 days from receipt;
- Avalon-held complete structured crash and exception reports, including the EU internal sink and any Global pre-forward copy: 90 days;
- EU-internal content-minimized crash issue history: rolling 13 months; each occurrence bucket and resolution annotation expires independently, first/last seen and counts are recomputed from surviving contributions, and an issue with no surviving contribution is deleted;
- EU-internal semantic product analytics events: 13 months from occurrence.

Global claimed-epoch deletion indexes retain only as long as the attributable Avalon-held replay or receipt class can remain, at most 90 days after the last associated event. EU claimed-epoch and telemetry-subject deletion indexes retain only as long as the attributable EU event class can remain, at most 13 months after the last associated event. Both are removed sooner on account deletion. Active `preference_subject_handle` mappings are account configuration rather than telemetry; they rotate when region/account bindings change and are deleted with the account.

These retention and deletion requirements govern Avalon-controlled local, Global, and EU storage through destination acknowledgement and expiry of any internal replay copy. PostHog-side retention, deletion, profile handling, and issue-workflow configuration are owned separately and do not gate this internal platform design. User/workspace deletion resolves current and historical internal analytics identifier key versions, anonymous epochs claimed by that person, and region-scoped EU telemetry/preference handles; suppresses future delivery; deletes queued and stored regional records; and records completion without retaining the deleted identifier. Raw dumps are addressable by regional subject/install index where consented identity exists; truly anonymous pre-auth dumps expire by retention rather than pretending they are attributable.

Access to Avalon-held telemetry follows least privilege. Product analysts see approved Global events after delivery to PostHog and approved EU events only through Avalon's internal regional analytics access. Engineering sees the full sanitized structured Global report in PostHog and the equivalent EU report through the internal issue surface. Only a small audited support/security role can retrieve a raw dump or unsanitized internal artifact, and only from the matching Avalon crash store. PostHog access and lifecycle configuration are administered separately from this internal platform design.

Flags may reduce sampling or disable a schema or destination, but no remote feature flag is a privacy boundary. Collection code must enforce the compiled allowlist and effective consent even when configuration is stale or incorrect.

### Acceptance criteria

The PRD is implemented when all of the following are true:

1. A typed tracking plan lists every production event, allowed source, property, classification, owner, retention, sampling, and authoritative outcome; CI rejects unregistered events and incompatible schema changes.
2. Renderer code has no PostHog or general analytics SDK, provider key, generic capture API, or direct telemetry network path. Tests prove that only the narrow preload contract reaches main.
3. Normal events from Global and EU desktop sessions reach only their configured regional ingestion and durable storage. Before explicit selection, an existing workspace binding wins; otherwise Cloudflare's coarse EU-country result routes anonymous-epoch and identity-scoped onboarding events immediately to the EU internal sink or Global/PostHog. There is no region-pending event store. EU has no PostHog credential or telemetry egress path. Cross-region integration tests fail if an event, dump, stack, source artifact, derived report, or credential takes any path other than the allowlisted immediate Global-to-EU onboarding RPC. The EU onboarding projection may carry only the applicable anonymous epoch or dedicated EU telemetry subject handle, never a raw platform or Global destination identity. The account-preference RPC is separately verified to carry only its opaque region-bound preference subject handle, boolean, expected/current version, and authenticated operation metadata.
4. Client intent and server outcome can be queried by `operation_id` without using raw user, workspace, or content fields. Clock-skew and duplicate tests produce deterministic results.
5. A regional API acknowledgement means the event is durably recorded or explicitly rejected; provider downtime does not lose accepted events within the documented retention and capacity limits. Every accepted row receives an immutable 90-day deletion deadline at acceptance, retry stops at that deadline, and success or terminal failure cannot extend it. Journey route and content-free delivery/deduplication metadata receive the same fixed ceiling at creation.
6. The Global PostHog project receives only fields in golden privacy fixtures. The adapter never forwards request IP, raw identity, detailed location, or an unregistered property. Internal Global rows, replay copies, and identity metadata obey their Avalon deadlines independently of destination acknowledgement, while PostHog-side lifecycle and profile configuration remain outside this PRD. The same fixtures prove that EU events never leave Avalon's Cloudflare-backed platform.
7. Packaged forced-error tests map main, preload, and renderer JavaScript frames through the matching private source map without uploading source maps or source excerpts to PostHog. Packaged forced-crash tests on every supported OS and architecture produce a route-final local dump, leave the live Crashpad database untouched, rotate the inactive database on the next launch, upload the eligible report from main with header-based authentication, match private native symbols to the correct release, and create a stable issue fingerprint. No credential appears in a Crashpad submission URL or URL-bearing log. Simulated long-running and dormant installations prove that a normal event or crash report older than 14 days is never delivered and that every expired rotated or unrotated file is physically purged before the next-launch delivery/rotation step. Region-change, opt-out, and workspace-policy tests prove that an invalidated active generation is never uploaded. Global delivers the complete golden-fixture-approved structured report to PostHog and proves that the raw dump, private artifacts, memory fragments, source excerpts, absolute paths, and unsanitized fields are absent. Breadcrumb fixtures cover `available`, `stale`, and `unavailable` sidecars rather than assuming lossless fatal-crash context. EU performs both JavaScript and native symbolication inside Avalon's isolated Cloudflare-backed deployment or marks a report unsymbolicated when that compute is unavailable, and exposes the equivalent structured report only through the internal regional issue surface.
8. JavaScript main, preload, and renderer errors; renderer gone; unresponsive/recovered; unclean exit; launch crash; and native crash each have a tested detailed signal while Product analytics is enabled and a tested content-free essential occurrence where applicable when it is disabled. Neither fatal path requires a graceful shutdown.
9. Crash-free launch/session calculations include only continuously reporting-eligible launches and sessions, disclose eligibility coverage and dropped, sampled, rejected, or rate-limited reports, and segment by release, platform, architecture, region, and channel. Tests cover enabling and disabling mid-session without moving an ineligible session into the crash-free denominator.
10. The account-scoped Product analytics setting defaults on and takes effect locally without waiting for a destination call. Turning it off stops new product events, JavaScript diagnostic payloads, breadcrumbs, and native dump upload; purges affected queued events; and keeps nonessential collection off until the regional API acknowledges the canonical account version. Other installations and server-native/asynchronous events honor the same persisted preference. Multi-installation, offline opt-out, stale-write, regional activation, queued-event suppression, and failure-to-resolve-policy tests all fail closed to essential telemetry only.
11. The anonymous bootstrap capability accepts only generated logged-out onboarding events; after authentication, the bootstrap session applies an existing user's canonical analytics preference before accepting platform-user product events. New users receive the approved default-on value, and no analytics toggle or consent interruption appears during onboarding. A locally known opt-out survives logout. If a fresh installation's default-on anonymous epoch later authenticates as an already opted-out account, Avalon closes the epoch and purges every attributable accepted event, sink record, secondary index, derived issue contribution, correlation, and outbox/replay copy through its original route before acknowledging internal completion; it recomputes affected EU issue state and issues no alias. Provider-held data follows separately managed PostHog configuration. For an eligible same-region transition, authentication automatically links the verified anonymous epoch to the derived person identity exactly once through the destination adapter; the desktop never receives provider identity authority. In Global PostHog, the alias command uses the anonymous epoch as `distinct_id` and the derived person as `alias`; anonymous epoch events set `$process_person_profile: false`. The lifetime installation identity is never aliased. Logout, account switching, and an abandoned login rotate the epoch before another account can claim activity. If the provisional telemetry region and authenticated workspace region differ, Avalon leaves the earlier epoch anonymous in its original region, creates no cross-region identity mapping, and starts person history prospectively in the explicit workspace region. Tests cover opt-out discovery, internal epoch purge from both the Global internal path and committed EU sink, alias direction, retries, closed epochs, two accounts sharing an installation, and prove that neither account inherits the other's epoch. They also prove that an explicit binding wins, inferred-EU events reach the EU sink once, non-EU, unknown, and geolocation-failure events reach Global/PostHog once, later explicit selection does not migrate or duplicate earlier events, raw platform and Global destination identities do not enter the EU sink, and no IP or detailed geolocation reaches storage, logs, event properties, or either analytics destination.
12. A workspace owner or administrator can disable Product analytics for the workspace, but cannot enable it for a user who opted out. Tests prove that user-off or workspace-off suppresses product events and detailed diagnostics at creation, regional acceptance, asynchronous emission, and destination delivery while essential reliability continues. Pre-workspace identity events have no workspace-policy term and use the canonical user preference plus provisional routing policy.
13. Before region selection, an inferred EU-country result prevents Crashpad from starting and no native dump or crash sidecar is created, stored, queued, or uploaded; non-EU, unknown, timeout, network failure, and unusable responses start Global-designated local capture. Tests prove the bounded route gate resolves or falls back before the first renderer is created, so non-EU/unknown renderers are covered from creation and EU pre-region capture remains intentionally absent. There is no region-pending crash store, and subsequent launches use an explicitly selected workspace region. The disclosure distinguishes provisional location behavior and its Global fallback from workspace-region processing.
14. Disabling native reporting stops Avalon's main-process dump uploader immediately. Avalon does not mutate a live Crashpad database. After restart and before Crashpad can start again, it purges the configured pending-report database and crash sidecars and verifies the purge in packaged tests. Tests cover database locks, a crash during the restart window, and an upload already in flight; the UI promises neither recall nor deletion until the regional deletion workflow confirms it.
15. Deletion tests cover current and rotated analytics IDs, identity-plane route metadata and delivery receipts, regional outbox rows, Global pre-forward and replay copies, crash indexes, and the EU internal sink. EU lifecycle fixtures advance past the immutable 90-day and 13-month deadlines and reconcile deletion from primary rows, secondary indexes, materialized views, crash correlations, and issue contributions; surviving issue aggregates are recomputed and emptied issues are removed. Corrupt-spool fixtures prove quarantined generations keep an externally stored absolute deadline and bounded byte budget, purge during startup/maintenance, and are deleted immediately when deadline metadata is invalid. Access to raw crash artifacts is regional, role-restricted, and audited. PostHog-held data after destination acknowledgement is outside this internal deletion test.
16. Rejection-path tests place synthetic secrets in unknown event names, schema strings, property keys, field paths, release fields, and payload fragments and prove that only fixed sentinels, registered identifiers, server-derived release identity, violation codes, and counts reach storage or logs.
17. The public site remains free of behavioral analytics until its separate rollout gate updates the Cookie & Tracking Notice and any required consent controls. Site tests then prove that only allowlisted aggregate-funnel events are accepted; the anonymous session identifier is cookieless and short-lived; EU-country traffic reaches only the EU internal sink; and no identifier is transferred through a download, deep link, installer, Electron launch, login, or account record.
18. Telemetry endpoint abuse tests cover payload size, schema bombs, compression bombs, malformed minidumps, replay, forged regions, event floods, and expired upload capabilities.
19. Product actions continue normally when the spool is full, the API is offline, the regional queue is delayed, the EU internal sink is unavailable, or PostHog is unavailable; aggregate loss is measurable.

### Success measures

Within the first two stable releases after full desktop rollout:

- at least 99.5% of valid, accepted normal events reach the configured destination within 15 minutes, excluding declared provider incidents;
- p95 telemetry ingestion adds less than 25 ms to API handler wall time because delivery is deferred after durable regional acceptance;
- desktop collection consumes less than 0.5% average CPU, 15 MB memory, and 1 MB/day network at the default sampling policy for a typical active user;
- 100% of sampled production event schemas pass the automated prohibited-data scan, with zero confirmed customer-content events in PostHog or the EU internal telemetry sink;
- at least 95% of forced and dogfood native crashes are symbolicated to an owned frame for releases whose symbols were published;
- release dashboards report crash-free launches and sessions with reporting-eligibility coverage and known delivery/drop denominators;
- the initial activation funnel has both client intent and server-confirmed completion for every state-changing step.

Volume, performance, and symbolication targets are engineering budgets rather than promises to customers. They are revisited after dry-run data establishes realistic baselines.

### Open product decisions

No product decisions remain open for the desktop/API release or the approved aggregate-only public-site scope. Legal and privacy review may require shorter retention or stricter site consent. Durable visitor-to-desktop attribution, an EU PostHog deployment, or any expansion of captured data requires a new recorded decision rather than an implementation assumption.

## Impact on the product contract

This PRD changes Avalon's external and internal product contract in material ways:

- Avalon begins collecting defined reliability and, when approved, product-usage telemetry from the desktop and API. The Privacy Policy, DPA annexes where applicable, subprocessor register, in-product settings, and support documentation must describe the categories, purposes, providers, retention, controls, and regional behavior before external rollout.
- The public site's existing no-behavioral-analytics statement remains true in the first release. A site rollout cannot occur as an implementation detail; it requires the notice and consent gate defined here.
- Workspace regional selection governs product telemetry, crash artifacts, symbols, delivery credentials, deletion, and support access once known. Before explicit selection, Cloudflare's coarse EU-country signal routes onboarding events immediately and suppresses pre-region EU crash capture; non-EU and unknown onboarding activity uses Global. Global may send approved telemetry to the US PostHog project. EU telemetry, dumps, and derived reports remain inside Avalon's isolated Cloudflare-backed platform; any future EU PostHog deployment requires a new recorded decision.
- Desktop users gain an account-scoped Product analytics setting in the normal authenticated Settings experience; onboarding does not gain another toggle or interruption. The setting defaults on and describes what is collected in plain language with a link to a field-category reference. Turning it off disables semantic product analytics, JavaScript diagnostic stacks and breadcrumbs, and native crash reporting on all installations once synchronized, while essential content-free reliability telemetry continues. The UI explains that fully stopping local Crashpad dump generation and purging its pending database requires a restart, although upload stops immediately.
- PostHog becomes a disclosed subprocessor or service provider only for the approved Global categories. This PRD's implementation and verification boundary ends when PostHog acknowledges an approved payload; provider-side contract, retention, deletion, access, profile, and product/model-development configuration are governed separately. EU disclosures describe the internal Cloudflare-backed path and any locality limitation of the selected primitives.
- A native minidump can contain memory fragments and therefore may contain customer content despite Avalon's minimization. It is never described as content-free; it is covered by the disclosed Product analytics master control and receives separate access and retention treatment.
- Telemetry does not become customer workspace content, a collaboration surface, or a source of product truth. It is advisory and can be incomplete because of policy, offline use, sampling, rate limits, or provider failure.

## Key design decisions

1. **Avalon owns the collection boundary and uses vendors as destinations.** The narrow Global bootstrap/identity ingest and regional workspace ingests are the only places that can consistently enforce routing, identity derivation, the tracking plan, user preference, durable delivery, redaction, and deletion across desktop and server signals. A direct renderer-to-PostHog integration and a thin reverse proxy are rejected because both leave policy and event semantics in an untrusted, independently released client. Buying a full Segment-like CDP is deferred because the first release has one external destination and Avalon already operates the relevant API boundaries.
2. **Product analytics defaults on per user and is the only user-facing control for nonessential telemetry.** A default-on setting preserves useful product and release evidence without requiring a first-run consent interruption. The control lives in authenticated Settings rather than onboarding. Turning it off disables semantic product events and every detailed diagnostic payload; only the compiled content-free essential allowlist remains. Workspace owners and administrators may further disable collection but cannot override an individual opt-out. A model where native dumps or JavaScript stacks continue after this setting is off is rejected because the label would understate the user's choice. A separate crash-only switch is rejected to keep the control understandable and avoid settings overhead.
3. **Global and EU use different destinations until Avalon operates an EU-specific PostHog instance.** Global sends approved projections to the current US PostHog project. EU events, dumps, artifacts, symbolication, and derived reports remain in Avalon-owned, isolated Cloudflare-backed primitives, preferring documented EU domicile and otherwise using dedicated EU-only primitives. Sending EU telemetry to the US project is rejected. Silently treating the existing shared Analytics Engine dataset as EU-resident is also rejected because its jurisdiction guarantee is insufficient.
4. **Automatic capture stops at content-free lifecycle and reliability signals.** Stable counters and bounded enums supply release denominators without depending on every feature author. DOM interaction, console, replay, and arbitrary network capture are rejected because Avalon's interface displays customer work content and mechanism-based scrubbing cannot supply a reliable semantic or privacy boundary.
5. **Pre-region onboarding routes immediately from a coarse Cloudflare location signal.** A narrow bootstrap endpoint covers the logged-out anonymous epoch and upgrades to the identity-only session after Google sign-in. An existing explicit workspace binding takes precedence. Otherwise the Global edge reads Cloudflare's `isEUCountry` result, reduces it to `eu` or `global`, and fixes that provisional route for the onboarding journey. EU-country events are validated and handed immediately to the EU internal sink; non-EU, unknown, and geolocation-bootstrap failures enter the Global PostHog path. No raw IP, detailed location, or region-pending event payload is stored. A later explicit selection changes future routing only, so an event routed provisionally is never migrated or duplicated. The discarded pending-store design is rejected because product chose immediate routing.
6. **Pre-region crash capture uses the same route but never exposes a credential in a URL.** A bounded pre-window route gate keeps Crashpad stopped for an affirmative EU-country result and starts local Global-designated capture for non-EU or failed location. Crashpad records locally; only the next launch rotates the now-inactive database and uploads eligible reports with authenticated headers. A telemetry-region or restrictive policy change invalidates the current capture generation, which is purged rather than uploaded on restart. Direct native upload and reading the live Crashpad database are rejected unless a future supported Electron API provides the same credential and lifecycle boundary.
7. **Global PostHog receives full sanitized structured crashes; EU stays internal.** Global sends the approved symbolicated frames, typed breadcrumbs when recoverable, fingerprint, release/process context, and session correlation to PostHog. Raw dumps, artifacts, memory fragments, source excerpts, and unsanitized fields remain in restricted Avalon storage. EU sends none of these records to PostHog and uses the equivalent internal report. PostHog-side retention, deletion, and workflow configuration are operated separately and are outside Avalon's internal storage lifecycle.
8. **Internal retention clocks are absolute ceilings where the process controls deletion.** Desktop normal events and local crash material lose delivery eligibility 14 days after creation. A running app purges them at that deadline; material on a dormant device may remain physically until the next application launch, when it is deleted before any delivery attempt or Crashpad restart. Avalon does not claim a background deletion guarantee while the app is not running, and a later launch can never restore eligibility. Accepted regional event/replay rows, terminal failures, route/receipt metadata, and schema-rejection contributions expire no later than 90 days from their respective creation or acceptance; a later event or delivery-state change never restarts an earlier contribution's clock. Received raw dumps and Avalon-held full structured crash occurrences retain 90 days. EU-internal minimized crash issue contributions and semantic product events use a rolling 13-month window. User/workspace deletion and opt-out suppression may remove internally held data sooner. Once Global data is accepted by PostHog, its lifecycle is governed through separate PostHog configuration rather than this internal architecture.
9. **Only a per-login anonymous epoch may link to a person.** Same-region authentication claims the current epoch exactly once through the destination adapter; the lifetime installation identifier never aliases. Logout, account switching, or login abandonment rotates the epoch. If the provisional and explicit workspace regions differ, the epoch remains anonymous in its original region and no cross-region identity bridge is created.
10. **The future public site measures only an aggregate funnel.** A separately gated site source may use explicit cookieless events, a browser-session identifier, and coarse campaign/referrer buckets. It cannot carry an identifier into downloads, Electron, authentication, or accounts. Durable visitor-to-desktop attribution, autocapture, replay, and advertising pixels are rejected.
