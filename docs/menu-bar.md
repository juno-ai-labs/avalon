# Menu bar item

Rally puts a status item in the macOS menu bar. Beside the icon it shows the
number the sidebar's rail counts: each Sidekick waiting on input or holding
something unread, plus each Canvas holding something unread. Clicking it drops
down a menu with two sections: **Needs attention**, the top five of those, and
**Recent Canvases**, the five most recently updated Canvases. Below them are the
two controls that keep the app reachable when nothing else is on screen: open
Rally, and quit.

**Every row reopens something that already exists.** The menu starts nothing at
all: no Canvas, no Sidekick, no meeting or note.

It is the one Rally surface that outlives every window. Rally registers itself
to open at login by default and, on a login launch, opens **no** window at all,
so on a freshly started Mac the menu bar item is the whole application until
someone asks for more. That is why nothing here is read through a renderer:
the main process holds its own workspace socket and, from it, the same two
lists the sidebar draws.

The shared workspace watcher recovery policy and phase diagnostics are owned by
[`websocket-architecture.md`](websocket-architecture.md#reconnect-and-teardown).

### The item

`MenuBarController` reads `menuBarEnabled` at launch and creates an Electron
`Tray` when it is on. The image is a macOS **template image**: black pixels plus
an alpha mask, which AppKit recolors for whichever menu bar it is drawn into.
That is the only treatment that stays legible on macOS 26 and 27, where the menu
bar is translucent and the desktop picture shows through it, and it is also what
makes the item follow light mode, dark mode, and a highlighted item without any
appearance handling of Rally's own. The filename's `Template` suffix sets this,
and `setTemplateImage(true)` says it again so a rename cannot quietly turn the
mark into a black blob. `nativeImage` resolves the `@2x` sibling by name.

### The count

`MenuBarController.refresh()` sets the tray's title (`Tray.setTitle`, which
macOS draws to the right of the icon) to the number of rows Needs attention
holds — every one, not the five the menu lists. `menuBarTitle` formats it as the
rail's badge — `99+` past two digits, nothing at zero — and it is empty while
signed out.

**It is the rail's number.** The rail's Canvases and Sidekicks badges are
`useSectionCounts` in `navigation-sidebar.tsx`: Canvases counts each Canvas
whose row is `unread`, Sidekicks each Sidekick whose row is `needsInput` or
`unread`. Both rules are two predicates in `common/sidebar-attention.ts`, and
`menuBarContent` calls the same two on the same two lists, read from the same
socket frames, so the menu bar and those two rail badges cannot disagree for
longer than one push takes to land. The dock badge is not this number: it is
the unseen Activity count (`dockBadgeCount`), the count a push sets on the
icon while Rally is closed ([`desktop-shell.md`](desktop-shell.md)).

### The menu

The drop-down is rebuilt from `menuBarMenuTemplate` whenever the content or the
preference changes — never on open. A click therefore always produces a menu
immediately. In order:

1. **Needs attention**: each Sidekick that needs input, sublabel **Needs
   input**; then each other Sidekick holding something unread, and each Canvas
   holding something unread, sublabel **Unread**. Five rows in all, each kind
   in the server's list order (Sidekicks by title, Canvases by recency); the
   sidebar's Pinned group is not applied. Under the header, **Still loading** until both
   lists have arrived, and **Nothing needs your attention** only after they
   have, so a waiting list is never called empty.
2. **Recent Canvases**: the first five Canvases, re-sorted here by
   `updatedAt`, newest first, with the id breaking a tie so equal times keep
   one order. With none, **Still loading Canvases** until
   the list has arrived, and **No Canvases yet** only after it has.
3. A separator, then **Open Rally** and **Quit Rally**.

A row with no title yet reads **Untitled**: a native menu row cannot draw the
skeleton the sidebar does.

Signed out, both sections collapse to one **Needs attention** header over
**Sign in to Rally**: there is nothing to list in either.

Headers use `type: 'header'`, which macOS added in 14 and which AppKit
styles as a real section header. `supportsSectionHeaders` reads
`process.getSystemVersion()` and falls back to a disabled row below that —
unclickable either way, because a header that could be activated is a menu row
that does nothing. `sublabel` needs macOS 14.4; earlier versions draw the row
without it.

Separators are pushed only between sections; the menu opens directly on its
first header.

Rows carry titles somebody's model wrote. A macOS menu is as wide as its widest
row, so `menuBarLabel` collapses whitespace and truncates at 60 characters,
trimming back to the last whole word when one falls within the final 20 and
cutting hard otherwise. Punctuation left dangling by the cut is dropped, and
the ellipsis fits inside the limit rather than pushing past it.

**The menu starts nothing.** This surface is for getting back to work that is
already in flight; the two rows at the bottom open the app, where starting
something belongs.

**No client feature flag reaches the main process.** A future main-process
surface that needs a flag re-adds the channel.

**The menu carries no login-item control.** It is rebuilt only when its content
moves, and macOS can change the login item from System Settings at any time, so a
checkbox here would go stale with nothing to correct it. Settings owns that
preference and reads it fresh — see below.

Every row re-enters through the existing deep links rather than through a
second navigation path, so a menu row and a link clicked anywhere else land in
the same place: a Canvas row emits `canvasDeepLink` and a Sidekick row
`sidekickDeepLink` ([`links.md`](links.md)), each for the active credential's
Organization, which the renderer opens at `/canvases/:id` and `/sidekicks/:id`.

Rows carry `app.focus({ steal: true })` before they act. A status-item click does
not activate the application the way a Dock click does, so a window opened
without it appears behind whatever is frontmost.

### The content

**The main process holds a workspace socket of its own.** Both lists are
socket-owned: only the workspace socket carries them, and a renderer is not
there to ask on a login launch or after the last window closes.
`SidebarListsWatch` therefore holds them from the same frames the renderer's
socket applies, but only the fields the menu reads: a Canvas's id, title,
`unread` and `updatedAt`; a Sidekick's id, name, `needsInput` and `unread`.

- It dials through `watchWorkspaceSocket` with a ticket from
  `GET /workspace/socket`, over the main-process Node broker's route
  (`createNodeRealtimeSocketFactory`), so it takes the system proxy, the
  operating system's certificates and the Rally `Origin` the feed sockets
  take.
- Each subscribe answer's `sidebar` replaces both lists whole, whatever was
  held: nothing is replayed across a reconnect, so the answer is the only
  record of what moved while the socket was away.
- A pushed `workspace_canvas_list`, or a `workspace_sidebar_list` for
  `automations`, replaces its list when its waterline is newer than the one
  held, and is dropped otherwise — the same rule `applyVersionedSidebarList`
  applies in the renderer, so a push overtaken by a fresher answer cannot
  bring an old list back.
- The socket sends nothing beyond subscribe and the heartbeat ping: no
  request, no presence, no command.

Changes are coalesced to one menu rebuild per microtask, so a subscribe answer
and a burst of pushes do not each rebuild the native menu.

`syncMenuBarDirectory` in `index.ts` decides whether the socket exists. It runs
on every session change, on the preference moving and at launch, reads the
active credential from storage (a login launch has no in-memory session yet),
and opens one socket per account and Organization; a token renewal keeps it.
No socket exists while signed out, for a guest, off macOS, or with the
preference off. A sign-out stops it synchronously, before the queued sync runs,
and stopping forgets both lists.

This is a second workspace socket per desktop while a main window is open, which
[`websocket-architecture.md`](websocket-architecture.md) otherwise keeps to one.
It is the price of a count that is correct with no window, and the cheapest
option to reverse: the alternative, the main window publishing its lists to
main over IPC, leaves the menu bar with no count at all once the last window
closes.

Opening the drop-down emits the product event `menu_bar_opened` with whether
the account is signed in, the bounded recent-row count, and `attentionCount`,
the rows in Needs attention. Before 2026-11-07 it counted unread Activity rows,
and before 2026-10-13 waiting threads, so a chart over it steps at each of
those releases. The legacy pinned count is always zero. Electron can notify one
opening through both the Tray click and the Menu `menu-will-show`;
`MenuBarOpenObserver` coalesces those until `menu-will-close`, so one visible
menu is one event. Selecting an enabled row emits `menu_bar_action_selected`
with a closed action enum — `attention_conversation` for a Needs attention row,
`recent_workstream` for a Recent Canvases one — whose values come from
`TELEMETRY_MENU_BAR_ACTIONS` in the registry. The names predate Canvases and
are kept because the enum is admitted at ingestion. It never includes a title
or identifier, and reporting cannot block the selected action.

### Opening at login

`LaunchAtLoginController` registers Rally with `app.setLoginItemSettings({
openAtLogin: true })`, which is `SMAppService.mainApp` on macOS 13 and later. The
registration is made once, on the first packaged launch that finds
`launchAtLoginDefaultApplied` unset, and the marker is written only after the
registration succeeds.

**macOS, not `application-settings.json`, owns whether Rally opens at login.**
Someone can remove the item in System Settings → General → Login Items, and a
preference file that disagreed would put it back unasked. The file records only
that the default has been spent. The controller reads `openAtLogin` back after
every write, because macOS can hold a registration in `requires-approval` until
the person allows it, and Settings has to show what is true rather than what was
asked for.

The toggle lives in Application → **Startup**, and only there. Its state comes
from `DesktopApplicationSettings.launchAtLogin`, which the main process fills
from the operating system on every read.

After launch initialization, Product analytics records that actual state and
whether login items are available as part of `application_settings_state_v2`. A
successful Settings interaction records `application_setting_change_completed_v2`
with the previous, requested, and read-back applied booleans. This is deliberately
not a renderer click: macOS may keep an enable request off while approval is
pending, and analytics must preserve that distinction.

### Detecting a login launch

`launchedAtLogin` answers the question the whole hidden-launch behavior rests on,
and macOS answers it directly: `app.getLoginItemSettings().wasOpenedAtLogin` is
set on a launch that came from a login item, and unset when a person opened
Rally from the Dock, Finder, Spotlight, or a deep link. `--hidden` is honoured
alongside it, which is how the path is exercised without waiting for a real
login.

Nothing distinguishes a login from a restart — both are one login event to macOS
— and Rally treats them the same. When the flag is set **and a status item is
actually in the menu bar**, `whenReady` skips `createMainWindow` entirely. The
second half matters: the item is off whenever someone turned it off, and absent
whenever creating it failed, and hiding into a menu bar item that does not exist
leaves Rally running with nothing on screen. `MenuBarController.present()` is
that question, and it is deliberately not `enabled()`. `app.on('activate')` still builds a window when the
Dock icon is clicked, and a deep link still builds one on the way to its
destination, so the hidden state is not sticky.

## Invariants

- **The main process, not a renderer, owns the menu's content.** A launch at
  login has no window, so anything that asked a renderer for the list would show
  an empty menu exactly when the menu is the only surface there is.
- **The menu is built from what the main process holds, never fetched on
  open.** A drop-down that waited on the network would hang under the pointer
  on a bad connection. Freshness arrives as socket pushes.
- **Signing out forgets every row, including whatever is still on the wire.**
  The previous account's Canvas and Sidekick titles are workspace content.
  `stop()` closes the socket and forgets both lists; a frame from a closed
  connection never reaches the watch.
- **A launch opens no window only when there is a status item to hide into.**
  Otherwise Rally starts invisible with no menu bar presence, reachable only by
  hunting for it in the Dock. The Startup toggle's own copy says so, because the
  quiet start is what it promises.
- **`menuBarEnabled` is a preference; `menuBarPresent` is a fact.** Both cross
  the bridge, because a toggle that succeeded and an item that exists are
  different claims and only the second one is what the person asked for.
- **One count, one rule.** The number beside the icon is the Needs attention
  rows, all of them, and those rows are what the rail counts. A row or a count
  from anywhere else would disagree with the rail and the dock, which is the
  mismatch this design exists to avoid. The rule is shared, not copied: both
  call the predicates in `common/sidebar-attention.ts`, so a change to what
  counts is one edit there.
- **A list is "none" only once it has arrived.** `null` is not yet heard and
  `[]` is empty; the menu says **Still loading** for the first and the empty
  copy only for the second.
- **Menu analytics are structural, never content-bearing.** Open events carry
  booleans and counts, action events carry one enum, and the enum lives in the
  registry rather than being retyped beside the producer. Titles and provider
  account IDs remain outside telemetry.
- **A retired action value stays admitted, and stops arriving.** The registry
  schema is what accepts an event at ingestion, and released clients keep
  emitting what their build offers. A value's presence in
  `TELEMETRY_MENU_BAR_ACTIONS` means some shipped build emits it, never that the
  current menu offers it.
- **The socket exists only where a menu can be built.** Otherwise it is a
  standing connection and workspace titles held in memory for nobody — on every
  non-macOS install, and with the preference off.
- **The status item is torn down on `will-quit`, never `before-quit`.** A
  `before-quit` can still be held (the shutdown-telemetry barrier prevents the
  first one and resumes the quit later), and a teardown that has already run by
  then leaves Rally alive with no window and no menu bar presence.
- **The login item is read from macOS, never from a field.** It can be removed,
  added, or approved in System Settings while Rally runs, and nothing announces
  it; `enabled()` therefore re-reads on every call.
- **The `Template` filename suffix and `@2x` sibling are load-bearing.** Losing
  the suffix gives a black square on a dark menu bar; losing the `@2x` file gives
  a blurred mark on every Retina Mac. Neither fails a build, so
  `verify-macos-app.mjs` checks both are in the bundle.
- **`menuBarEnabled` reads as on when it is missing or unreadable.** The item
  ships on, and any other reading would silently withdraw it from every device
  that upgraded.
- **A header is never drawn with nothing under it.** Each section either has
  rows or says in a disabled line why it has none.
- **The menu never renders state the operating system can change behind it.**
  It is rebuilt on content changes, not on open, so anything macOS owns
  independently — the login item is the case that came up — belongs in Settings,
  which reads fresh.
- **A development build never registers a login item by default.** Its executable
  is a shared Electron binary in `node_modules` that would outlive the checkout.
  The toggle still works; only the automatic registration is withheld.
- **A failed status item is a degraded menu bar, not a failed launch.** Every
  action the menu offers also exists inside the app.

## Boundary

This module owns the status item, its menu, the data behind that menu, and the
login-item registration. It exposes two IPC channels —
`application-settings:set-menu-bar-enabled` and
`application-settings:set-launch-at-login` — and four fields on
`DesktopApplicationSettings`: `menuBarEnabled`, `menuBarAvailable`,
`launchAtLogin`, and `launchAtLoginAvailable`.

It does **not** own: the application menu bar at the top of the screen
(`application-menu.ts`), the Dock and Finder icon
([`desktop-icons.md`](desktop-icons.md)), what a Canvas or Sidekick link means
([`workstream-links.md`](workstream-links.md)), the lists' shapes and their waterlines
([`websocket-architecture.md`](websocket-architecture.md)), or session storage
and refresh — it borrows `loadStoredAuth` and the coalescing refresh and adds
nothing to them.

It depends on the deep-link vocabulary already handled in `app-session.tsx`.
Adding a menu row that navigates somewhere new means adding the link there
first, not a second navigation channel here.

What counts as needing attention is the rail's (`useSectionCounts` in
[`desktop-shell.md`](desktop-shell.md)), not this module's; both read it from
`common/sidebar-attention.ts`.

## Failure modes and limits

| Situation | Behavior |
| --- | --- |
| The socket drops | `watchWorkspaceSocket` redials with the shared backoff and logs the close. The lists already held stay on screen; the next subscribe answer replaces them. |
| A subscribe answer cannot be read | Logged with the rejected fields (`describeZodIssues`); the lists already held stay. |
| A push arrives older than the list held | Dropped by its waterline. |
| The server ends the session's access | The watch stops redialling (`stopped`), logs it, and forgets both lists, so no title or count outlives the access. The next session change opens it again. |
| The active workspace is a guest's | No socket. Both lists read as arrived and empty, so the menu says **Nothing needs your attention** and **No Canvases yet** rather than loading forever. |
| Signed out | One **Needs attention** header over a disabled **Sign in to Rally** row, a rule, and the two trailing controls. No number beside the icon. |
| A label runs long | Truncated to 60 characters at the last word boundary in the final 20, hard otherwise. |
| Nothing waiting, or no Canvases | The section's header over one disabled line saying so. |
| More than five waiting | Five rows; the number beside the icon counts them all. |
| A push arrives while the menu is **open** | Applied to the next build. macOS owns an open menu and nothing can redraw it underneath the reader. |
| macOS 13 or older | Every header falls back to a disabled row. Everything else is unchanged. |
| The login item registers but the marker fails to write | The registration is reported as it stands, not as off. The marker is retried on the next launch. |
| The login item cannot be read | The last answer is kept rather than reported as off, which would be a claim about a system this cannot see. |
| No status item on this platform, or the preference is off | No socket is opened. Turning the preference off closes it. |
| The `Tray` cannot be created | Logged and skipped, and Settings says so beneath the toggle — the write succeeded, so without that the switch reads on beside an empty menu bar. The preference stays on, so the next launch tries again. |
| The preference file cannot be read at launch | `initialize` still settles presence, falling back to the shipped default of on. Skipping it would leave `enabled()` true with no tray, and the caller fetching content nothing can render. |
| Not macOS | No status item; `menuBarAvailable` is false and Settings omits the toggle. The preference is still stored, so the same profile on a Mac gets the choice rather than the default. |

`menuBarLabel` counts and cuts in **graphemes**, via `Intl.Segmenter` — a title
can carry an emoji, and a cut by UTF-16 code unit leaves a lone surrogate
rendering as `�` in front of the ellipsis. The segmentation is skipped when the
code-unit length already fits, so the ordinary label never pays for it.

The empty-state copy is exempt from `menuBarLabel`'s 60-character limit. That
limit stops one model-written title stretching the menu; the fixed copy is ours,
has to read in full, and sets the menu's width only for an account that has
nothing in the section it belongs to.

Numbers: five rows per section (`MENU_BAR_SECTION_LIMIT`, the product
contract), 60-character labels (`MENU_BAR_LABEL_MAX_LENGTH`) with a word
boundary honoured from 40 (`MENU_BAR_LABEL_WORD_BOUNDARY_FLOOR`), and the
workspace socket's shared heartbeat and reconnect numbers. The ticket request
uses `rallyApiRequest`'s 8 s timeout.

## Testing

```text
pnpm --filter @rally/desktop exec vitest run src/main/menu-bar-menu.test.ts \
  src/main/menu-bar-content.test.ts src/main/menu-bar.test.ts \
  src/main/sidebar-lists-watch.test.ts \
  src/main/menu-bar-open-observer.test.ts src/main/telemetry-reporter.test.ts \
  src/main/launch-at-login.test.ts
pnpm --filter @rally/contracts exec vitest run src/workspace-reach-watch.test.ts
```

`sidebar-lists-watch.test.ts` drives `SidebarListsWatch` with frames shaped as
the server sends them — parsed by the contracts' own schemas — so the subscribe
answer, the pushes and the waterline guard run without a network. It cannot
prove the server sends those frames; the renderer's socket tests and
[`websocket-architecture.md`](websocket-architecture.md) own that.

Nothing here imports Electron at runtime. `menu-bar-menu.ts` builds a plain
template object, and the controller and watch take their Electron and socket
surfaces as injected dependencies. The template's `click` handlers are typed
with the menu item, window, and event AppKit passes but ignore all three, so
tests call them through a cast. The renderer Settings shell shows disabled
controls while `getApplicationSettings` is pending; a test for an unavailable
menu bar waits for the menu-bar control itself to disappear.

The status item itself cannot be verified in the sandbox — see
[`dev-environment.md`](dev-environment.md#what-cannot-be-verified-in-a-sandbox).
Nor can the windowless launch: it is gated on a status item being present, and
off darwin there never is one.

## Security and trust model

The renderer's only reach into this module is
`application-settings:set-menu-bar-enabled` and
`application-settings:set-launch-at-login`, each of which takes a boolean and is
rejected for anything else. The menu itself is built in the main process from
values the API returned, and its rows carry identifiers the main process
received rather than anything a renderer supplied.

`rallyApiRequest` is a main-process caller of the stored credential. Here it
reaches only `GET /workspace/socket` for a ticket, and adds no credential
storage of its own. The socket is listen-only; it sends nothing beyond subscribe and
the heartbeat ping — no request, presence or command. Canvas and Sidekick titles are workspace content and are held in
main-process memory only — never written to disk — and are dropped on sign-out
(`stopMenuBarDirectory`).

`menuBarEnabled` and `launchAtLoginDefaultApplied` share
`application-settings.json` with Lockdown mode, so they go through the same
shared write queue: a lost update there would leave an off Lockdown preference
beside a Lockdown envelope, which the next launch reads as an out-of-app edit and
answers by deleting the stored credentials. See [`security.md`](security.md).

Selecting a menu action that raises Rally also records
`application_opened(entrypoint=menu_bar, phase=activation)`. The explicit source
is reported before `app.focus`, so the application-open coalescer suppresses the
generic Electron activation callback rather than also counting a Dock open.

## Changelog

### 2026-11-08 — The dock badge leaves Needs attention for unseen Activity; the menu bar stays

**What changed:** The dock badge no longer adds up the rail's Canvases and
Sidekicks counts; it is the unseen Activity count. The menu bar's title and
Needs attention are unchanged: the Canvases and Sidekicks rows that need
attention.

**Why:** The owner said "fix this" on 2026-11-08 for the dock badge clearing
when an alert arrives while Rally is closed. The push badge is now the unseen
Activity count, so the open app writes the same number, which ends the
2026-11-07 rule that the menu, the rail and the dock are one number. The menu
bar lists rows, and its count has to match the rows under it (the 2026-10-13
rule), so it keeps counting them.

**Considered and rejected:** Moving the menu bar to unseen Activity as well:
its menu lists Canvases and Sidekicks, not Activity rows, so the title would
count things the menu does not show.

**Consequences:** The menu bar's title and the dock badge can differ.

### 2026-11-07 — Needs attention is what the rail counts; the Channel and Activity watches are deleted

**What changed:** The menu is built from the Canvases and Sidekicks lists,
which `SidebarListsWatch` holds over the main process's workspace socket.
Needs attention, and the number beside the icon, are each Sidekick waiting on
input or holding something unread and each Canvas holding something unread —
the rail's `useSectionCounts`. **Most recent** became **Recent Canvases**,
newest `updatedAt` first. `ChannelDirectoryWatch`, `ActivityFeedWatch` and
`common/recency-groups.ts` are deleted, and with them the Space walk, the
Activity REST read and the access-request rows. The socket now sends nothing.

**Why:** The client pivot to two sections (Canvases, Sidekicks) removed
Channels, Threads, Breakouts, Activity and access requests from the product,
so neither list the menu read exists in the app any more. The dock badge moved
to `useSectionCounts` in the same pivot; reading the same two lists here keeps
the 2026-10-13 rule — a count that matches the rows under it — and extends it
so the menu, the rail and the dock are one number.

**Considered and rejected:** Retiring the menu bar item with the features it
listed. It is still the whole application on a login launch, and the two lists
carry exactly what it needs. Keeping a REST read for either list: both are
socket-owned and pushed with a waterline, so a read would only add a request
per change and a second ordering rule.

**Consequences:** `menu_bar_opened.attentionCount` changed meaning again. The
telemetry action names `attention_conversation` and `recent_workstream` are
kept for the new rows because the enum is admitted at ingestion. Something that
should appear in Needs attention must change what the rail counts, and
`menuBarContent` with it.

### 2026-10-13 — Needs attention is the Activity tab's unread rows

**What changed:** Needs attention, and the number beside the icon, now come
from the Activity tab's feed (`GET /navigation/activity`) rather than from
`attentionItems` over the Channel rows. `ActivityFeedWatch` holds the first
page and reads it again when the workspace socket names the `activity` topic;
`ChannelDirectoryWatch` hands its sync topics on through `onSync`. Marking
Activity read now publishes `activity` to the reader's own sockets. The Channel
rows the watch keeps lost every unread, mention and attention field, and
`attention-items.ts` moved from `common/` to `renderer/lib/attention-ranking.ts`,
since no main-process code reads either any more.

**Why:** The menu and the Activity tab disagreed in front of the person: the
menu said "Nothing needs your attention" beside a tab full of unread dots.
Each was right by its own rule. `attentionItems` clears a thread once it is
opened, while an Activity row stays unread until **Mark all read**, and the
two lists hold different things (threads, against events about threads). The
product owner chose the tab's list for the menu, and a count that matches the
rows under it.

**Considered and rejected:** Clearing Activity rows when their thread is
opened, which would change the tab rather than the menu. Keeping the count on
`attentionItems` so it matches the dock and the Threads badge, which leaves a
number that disagrees with the rows under it. Re-reading Activity on every
Channel row push, which would cost a read per message across the
Organization when the `activity` topic already says when the feed moved.

**Consequences:** The number beside the icon can differ from the dock badge
and the Threads button's badge, which still count `attentionItems`. Every
message in the Organization publishes `activity` to everyone, so every desktop
with the menu bar on (the default, from login, with or without a window) reads
the 250-row Activity page once per burst of messages anywhere in the
Organization, two reads at most per burst. The renderer reads it only while
the Activity tab is shown, so this is a standing cost the tab never had. If
that read shows up in the Worker's load, the fix is a narrower topic, not a
cache here. `menu_bar_opened.attentionCount` changed meaning with this
release. Before this change "Mark all read" told no other
socket at all; another window's Activity tab now clears too. Something that
should appear in Needs attention belongs in the Activity feed
(`digests.md` (retired)), and must publish `activity`
when it moves, or the menu will not see it until the next reconnect.

Shipped in #1224.

### 2026-10-08 — The menu bar socket drops sends while closing

**What changed:** `reachSocketFromRealtimeClient`, the adapter the menu bar's
workspace socket dials through, now drops a send and an arriving frame once
its Node client is closing or closed, as a browser `WebSocket` does. It used to
pass the send to the broker client, which throws when the socket is not open.

**Why:** The watcher's heartbeat sends `ping` from a timer. After the Mac woke
from sleep, a socket the watcher had already started closing (pong timeout or
a socket error) could still see that timer fire, or a late `pong` re-arm it,
before the close event arrived. The throw escaped the timer and Electron showed
an "Uncaught Exception: Realtime socket is not open" dialog.

**Considered and rejected:** Catching the send inside `watchWorkspaceSocket`.
The renderer and lite hosts hand it a real browser `WebSocket`, which never
throws there; the Node adapter was the one breaking the shape it claims.

**Consequences:** `ReachSocket.send` on a closing socket is a no-op on every
host, so the watcher and `WorkspaceSocketConnection.send` need no guard of
their own.

### 2026-10-06 — A count beside the icon, and Needs attention over Most recent

### 2026-09-11 — `pushGroup` makes a bare header unrepresentable

**What changed:** `pushGroup` took back the empty-state guarantee it lost
earlier in this change, in a stronger form: it owns the separator above its
section, takes an optional `emptyLabel`, and draws one of exactly three things —
the rows, that line, or nothing at all. Call sites no longer push their own rule
or assemble their own fallback row.

**Why:** review caught that the refactor had quietly dropped a structural
guarantee. The original helper took the empty line as a *required* argument, so
a section could not be added without saying what to draw when it had no rows.
Moving the fallback out to the callers turned that into a convention, and a
convention is what the next section added through this helper would have
ignored: pass an empty array, get a header with a rule on either side and
nothing between them.

**Considered and rejected:** restoring the required `emptyLabel`. The recency
groups cannot be empty — `groupActivityItems` drops a heading with nothing under
it — so requiring a line for them would mean inventing copy no one can ever see,
which is worse than the hole it closes. Dropping the group entirely is the
honest answer for a section with nothing to say and no message about it.

**Consequences:** the separator moved inside the helper, so the "never a leading
rule, never two in a row, never a trailing one" property now falls out of the
same three outcomes rather than being maintained at each call site. A section
added here that needs its own rule placement has to change this helper rather
than work around it.

### 2026-09-11 — A heading that expires is rebuilt before it is read

**What changed:** `MenuBarController.refreshIfHeadingsExpired()` rebuilds the
drop-down from cached content when a recency boundary has passed since the last
build, guarded by `nextRecencyBoundary`. The pointer reaching the status item
calls it, before the content refresh rather than after. The controller now takes
an injectable `now` and passes it to the template, so the boundary it records
and the headings it builds read the same clock.

**Why:** review of #700 caught it. The recency headings are a function of the
content *and* of the time, and the menu was rebuilt only when content changed.
That is wrong in the case that matters most: a refresh that fails publishes
nothing, so it rebuilds nothing. Offline across midnight, the menu kept saying
**Today** indefinitely, and a work stream sat under a heading the sidebar had
already moved it out of. The 15-second staleness window hid the smaller version
of the same bug, where a pointer arrival skipped the fetch and so skipped the
rebuild with it.

**Considered and rejected:** a timer on `nextRecencyBoundary`, which is what the
sidebar does. A renderer is already awake and painting; the main process is not,
and waking it to redraw a menu nobody is looking at buys a heading that is
correct only in the moments nobody reads it. The pointer arriving is both free
and late enough, and it is the same hook the content refresh already uses.

Also rejected: rebuilding unconditionally on every pointer arrival. The
crossing fires whenever anyone passes the status item, and the guard makes the
overwhelmingly common case — nothing expired — a comparison rather than a
`Menu.buildFromTemplate`.

**Consequences:** a boundary passing while the menu is *open* is still not
covered and cannot be: macOS owns an open menu. Anything added to this menu
whose label depends on the clock has to go behind the same guard, or it
inherits the bug this entry fixes. The boundary is recorded only after
`setContextMenu` returns, so a build that throws retries on the next arrival
rather than going quiet until the boundary it never reached.

### 2026-09-11 — The menu became a way back to work, not a way to start it

**What changed:** Several things at once, because they are one decision. Every
row that started something is gone: the **Suggestions** section whole — header,
rows, impression report and start call — plus **New Work Stream**, **New
Automation**, and **New Meeting/Note**. **Pinned** moved above the recent list.
And the recent list grew from five rows to ten, now split into the sidebar's own
recency groups — **Last hour** through **Before this month** — instead of sitting
under one flat **Recent** header.

`groupActivityItems`, `nextRecencyBoundary`, `workstreamRecencyAt` and the
`RecencyGroup` union moved out of `renderer/lib/format.ts` into
`common/recency-groups.ts`; `format.ts` re-exports them, so no renderer import
changed. `MenuBarWorkstream` gained `lastActivityAt`, and the store fills it
through `workstreamRecencyAt` rather than from the raw field.

**Why:** the drop-down was trying to be two surfaces. Four of its rows started
something new, and the fixed vocabulary a person could learn was mostly made of
them — but the app itself is where you start work, and it is two rows away at
the bottom of this menu. What the status item is uniquely good for is the thing
no window offers: getting back into a work stream on a Mac that has no Rally
window open at all. Everything removed here was competing with that for the top
of a menu that has to stay a menu. **New Meeting/Note** was the closest call: a
meeting starts away from the keyboard, which is the one argument for starting it
from the menu bar. It lost to the same rule as the rest — the menu is a way back
in, and the sidebar's own meeting button is one click further for someone who
already has Rally open.

Growing the recent list to ten and grouping it was the same judgement from the
other side. Five rows is not enough to find yesterday's work in, and ten
unheaded rows is a wall — the sidebar solved that already, and its headings are
the ones a person has learned. Sharing the implementation rather than copying
the boundaries is what stops the two lists disagreeing: they list the same work
streams, and grouping by `lastActivityAt` here while the sidebar groups by
`workstreamRecencyAt` would file the same work stream under two headings in one
running app.

**Considered and rejected:** keeping a **Recent** header above the recency
groups. macOS menus have one level of header, so it would have labelled the same
list twice with no way to show the nesting. The header now appears only over the
empty state, where there is no recency to name and a bare disabled sentence
would read as a stray broken item.

Also rejected: leaving the suggestion fetch in place against the day the section
returns. A poll nobody renders is recurring API traffic, an impression contract
that reports suggestions nobody saw, and workspace content held in main-process
memory for no reader.

**Consequences:** `menu_bar_opened` stops carrying `suggestionCount`, and its
`recentCount` bound moved from 5 to 10. `menu_bar_action_selected` stops
emitting `new_workstream`, `new_automation`, `suggested_work`, and
`new_meeting_note`. All four, and `suggestionCount`, stay *admitted* by the
registry — released clients keep sending them, and the registry schema is what
accepts an event at ingestion. Do not read a historical row as evidence the
current menu offers that row. The `menu_bar` meeting entrypoint likewise stays in
`createMeetingWindow`'s union and in `surfaceEntrypoint`: a retired emitter, not
a retired value.

**No client feature flag reaches the main process any more.** The meeting row
was the last main-process consumer of one, so `observeClientFeatureFlags`, the
`feature-flags:observe` IPC channel, the `DesktopBridge` method, its preload
binding, and the two renderer call sites in `workspace-socket.tsx` were all
removed. Renderer surfaces read the same flags from the live workspace-socket
cache and are untouched. Whoever next needs a flag in main re-adds the channel;
keeping it warm for that would be an abstraction for a consumer nobody has asked
for, and a projection nothing reads is worse than one that does not exist. Note
that `MenuBarController` no longer has any input that changes between rebuilds
except its content and the sign-in state.

The menu is no longer a suggestion surface, so the invariant that a surface
showing suggestions must report them no longer applies to it. Should suggestions
ever come back here, that obligation comes back with them. (Suggested Work
itself was deleted on 2026-11-07; see [`data-model.md`](data-model.md#changelog).)

A recency heading is computed when the menu is built, which is when its content
moves — not when it opens. A row can therefore sit under **Last hour** for
longer than an hour on a menu nobody has touched. The refresh triggered by the
pointer reaching the status item is what corrects it, and waking the process on
a timer to redraw a menu nobody is looking at was not worth the wake.

### 2026-08-13 — Native navigation carries its proven entrypoint into the renderer

**What changed:** Main-to-renderer deep-link messages now carry a closed
entrypoint alongside the validated URL. Menu-bar navigation is marked
`menu_bar`, operating-system links are `deep_link`, and a meeting's note reveal
is `in_app_link`. The renderer records that source before changing routes.

**Why:** A URL alone proves the destination but not who initiated it. Treating
every native navigation as an unmarked hash change produced `unknown` or stale
surface attribution and hid menu-bar adoption.

**Considered and rejected:** Adding an untrusted query parameter to the custom
URL and treating every navigation as `deep_link`. Both lose the main process's
already-proven source.

**Consequences:** Any new native navigation producer must send one closed source
through the isolated bridge. The source is analytics context only and grants no
navigation authority; URL validation remains separate.

### 2026-08-13 — Menu opens, selections, login-item state, and successful suggested work are measurable, and a menu activation is not a Dock open

**What changed:** Each visible status-menu open now emits one bounded product
event despite Electron's duplicate click/show callbacks. Every enabled row emits
a closed action enum, while successful suggested-work adoption is emitted by the
regional API after creation with exposure context and `menu_bar` or
`workspace_home` as its surface. A menu action that raises Rally contributes the
explicit `menu_bar` application-open source before main focuses the app. Launch
initialization contributes the real login-item state and availability to the
bounded settings snapshot, and a completed Settings interaction records its
previous, requested, and macOS read-back applied state.

**Why:** Suggestion impressions answered ranking needs but could not answer how
often people opened the menu, which rows they chose, or whether a suggestion
actually became work. Selection alone also over-counts failures, so successful
suggested work needs the server commit as its boundary.

Focusing from a status item can also trigger Electron's generic activation
callback. Counting that callback independently would turn one menu interaction
into both a menu and Dock open.

A toggle click is not proof that macOS registered the login item; approval can
remain pending and the UI already reads the operating system back for this
reason.

**Considered and rejected:** Reporting labels, prompts, activity content, or
provider account IDs, and treating every click as a successful start. Those
approaches add content or corrupt adoption when creation fails. Opaque
opportunity/work-stream UUIDs are retained because they are required to join the
versioned exposure to its one created resource. Emitting only from the desktop
was also rejected because it cannot authoritatively distinguish a committed
start from an interrupted response.

For the open source: inferring it after focus or relying only on the existing
row-selection event. The former races Electron; the latter cannot join the same
canonical open-source analysis as system, Dock, and deep-link entrypoints.

For the login item: reporting the renderer click or requested boolean as the
new state. Either would count an unapproved registration as enabled.

**Consequences:** New menu actions must extend the closed action taxonomy and
its contract tests. Detailed start context is optional for compatibility with
released clients; current callers supply it and receive the detailed API event,
while an older request receives only the legacy successful-start fallback.
Telemetry remains observational and cannot prevent a menu action. The shared
open observer coalesces the two callbacks; menu row selection and application
opening remain distinct signals because a selection describes the chosen action
while an open describes how Rally was raised. The Product analytics preference
governs both login-item events; the login-item controller remains authoritative
and telemetry runs only after its mutation completes.

### 2026-08-11 — Rally gets a menu bar item, opens at login, and starts hidden

**What changed:** A macOS status item carrying the Rally mark as a template
image, with a drop-down for a new meeting or note, a new automation, the current
suggestions, and the five most recent work streams. Application → Appearance
gained **Show Rally in the menu bar**, on by default. Rally now registers
itself to open at login by default, offers that as a checkbox in the menu, and
opens no window when the launch came from the login item.

**Why:** Everything Rally can start required finding and raising a window first.
The status item makes the four things people actually start reachable from any
application, and opening at login is what makes it reachable without anyone
having launched Rally at all — which is only tolerable if that launch is silent,
hence the hidden start.

**Considered and rejected:**

- *Pushing the menu's content from the renderer over IPC.* It is less code and it
  reuses the React Query caches the home screen already has. It also fails in the
  one case that motivated the feature: a login launch has no renderer, so the
  menu would be empty exactly when it is the only surface. Fetching in the main
  process costs a second, narrower API client and is the reason the item works
  with no window open.
- *Parsing the full `WorkstreamSchema` from `@rally/contracts` for the recent
  list.* The menu reads an id and a title. Parsing the whole contract would let an
  unrelated field addition on the server empty the menu on an older client, so
  `menu-bar-content.ts` keeps its own narrow schemas and ignores everything else.
- *Storing whether Rally opens at login in `application-settings.json`.* macOS
  lets someone remove the login item from System Settings, and a preference file
  that disagreed would re-register it behind their back. The file records only
  that the enabled-by-default registration has happened.
- *`openAsHidden`.* It is the obvious Electron answer and it does nothing on macOS
  13 and later. `wasOpenedAtLogin` plus skipping `createMainWindow` is what
  actually works.

**Consequences:** The main process now makes API requests of its own, so
`avalonApiRequest` is the place to extend rather than a second ad-hoc `net.fetch`.
The menu's rows go through the existing `avalon://` deep links, so a new row that
navigates somewhere needs that link to exist first. Two resource names are
load-bearing and checked by the package verifier: the `Template` suffix and the
`@2x` sibling. And Rally can now be running with no window at all — anything
that assumes `mainWindow` exists after startup has to keep handling `null`, which
`sendDeepLink` and `activate` already do.

**Not done:** a submenu for older work streams.

### 2026-08-11 — Review round four: three failures that were reported as successes

**What changed:** `DesktopApplicationSettings` gained `menuBarPresent`, and
Settings says so when the preference is on and no item exists.
`MenuBarController.initialize` settles presence in a `finally`. A failed
impression report clears the recorded set only when nothing newer has been
recorded since.

**Why:** all three had the same shape — something failed and the surface above
it reported success. Turning the toggle on when `createTray` throws resolved
cleanly and reported `menuBarEnabled: true`, so the switch moved and the menu bar
stayed empty with nothing said. An unreadable preference file left `enabled()` on
its default of `true` with no tray, and the launch path then fetched and cached
work-stream titles that nothing could render. And clearing `recordedImpressions`
unconditionally on failure discarded the record of a *newer* set reported
successfully while the failing POST was in flight, so that set was reported twice
— the same double-count this field exists to prevent, arrived at from the other
direction.

**Considered and rejected:** having `set()` reject when `createTray` fails. It
reads as the honest thing and it is worse: the preference genuinely did change,
the next launch will retry it, and a rejected toggle would flip back and imply
the choice was not stored. Reporting the preference and the fact separately is
what lets Settings be accurate about both.

**Consequences:** `present()` now has two callers with different reasons — the
launch decision and the Settings report — so a change to what it means has to
answer both. `initialize` no longer guarantees the preference was read when it
returns; callers that need that must await it and handle the rejection, which
`index.ts` does by logging.

### 2026-08-11 — Review round three: the impression report never worked

**What changed:** `avalonApiRequest` decodes through `readJsonBody`, which reads
a 204 as `null` instead of rejecting. `startSuggestion` moves the generation
again once the POST resolves. `will-quit` replaces `before-quit` for the
teardown. Session changes and launch fetch content only when a status item can
exist. Two documents stopped claiming the windowless launch is checkable off
darwin.

**Why:** the impressions commit shipped inverted. `POST
/work-opportunities/impressions` answers `c.body(null, 204)`, `response.ok` is
true for a 204, and `response.json()` on an empty body rejects — so every open
logged a warning about a request that had succeeded *and* cleared the dedupe key,
which meant the once-per-set guarantee the whole commit was built around never
held once. Five opens on the same four suggestions reported five impressions,
over-reporting in the same direction the free-rider problem under-reported. The
test could not see it because the fake resolved a value the endpoint cannot
return.

The other three: the generation bump before the POST cannot cover a refresh
issued *during* it, because the service has not consumed the suggestion yet —
that answer legitimately still carries it, and `refresh()` then hands the caller
that stale request instead of a new one. `before-quit` fires before any window is
asked to close, and a meeting window vetoes; the status item was already gone by
then, with nothing to recreate it and Settings still reporting it on. And the
content fetch had no platform gate at all.

**Considered and rejected:** fixing the 204 inside `recordImpressions` by
tolerating a `SyntaxError`. That leaves the next no-content endpoint to
rediscover it, and it treats a decoding failure as success everywhere rather than
where a body is genuinely absent. Also rejected: gating the fetch on `present()`
rather than `enabled() && available()` — a status item whose creation failed
still has the preference on and is retried next launch, and content fetched
meanwhile is what that retry renders.

**Consequences:** `readJsonBody` is where a no-content Rally response is
decoded; a caller that goes back to `response.json()` reintroduces this for its
own endpoint. Anything that consumes a server-side resource has to move the
generation *after* the server agrees, not before — the sign-out case is the
exception precisely because the state has already changed when it fires. And the
impressions path is still the least-observed part of this module: it has no
end-to-end coverage, only the unit test and the decoding test that would have
caught this one.

### 2026-08-11 — Review round two: impressions, a stale login item, and a promise the copy could not keep

**What changed:** Opening the drop-down now reports its suggestions through
`POST /work-opportunities/impressions`. `LaunchAtLoginController.enabled()` reads
the login item from macOS on every call instead of returning the value this
process last wrote. The Startup toggle's copy no longer promises a windowless
login unconditionally.

**Why:** the menu was a free rider on the suggestion ranking. Impressions are
what tell it a suggestion was shown and passed over, and the ranking re-ranks on
them, so somebody who used only the menu bar would have seen the same four
suggestions indefinitely. The login item is owned by macOS and changeable from
System Settings at any moment with nothing announcing it, so a cached answer had
Settings offering to turn on something already on — and this document's own
acceptance step already told a tester to expect otherwise. The copy became untrue
the moment the launch started opening a window when no status item exists.

**Considered and rejected:** reporting impressions when the content is fetched.
It is one line and needs no menu event, and it is wrong in the direction that
matters — the fetch is triggered by the pointer reaching the status item, so it
would report suggestions nobody ever saw and push the ranking away from work
nobody has declined.

**Consequences:** the report is raised from both `menu-will-show` and the tray's
`click`, because which of the two macOS raises for a status item's own menu
cannot be checked here and reporting nothing is the failure being avoided; the
per-set key makes the pair idempotent, and anything that adds a third trigger
inherits that. `enabled()` now performs a synchronous `SMAppService` query on
every settings read — cheap, but it is no longer a field read, so a caller in a
hot path should hold the value rather than call it repeatedly.

### 2026-08-11 — Five defects found in review of the original build

**What changed:** (1) Cached content now carries a generation, bumped on
sign-out and on starting a suggestion; an answer that arrives under a stale one
is discarded, and `refresh()` no longer hands back an in-flight request issued
under it. (2) A login launch opens a window unless a status item is actually
present, which `MenuBarController.present()` now answers. (3)
`LaunchAtLoginController.initialize` reads the login item back in a `finally`.
(4) `menuBarLabel` cuts in graphemes rather than UTF-16 code units.

**Why:** each was a real failure, none reachable from the tests as written.
Sign-out emptied the cache but not the request already on the wire, so the
previous account's work-stream titles came back into the menu moments later —
the exact leak the method existed to prevent. A login launch checked the
*preference*, so with the menu bar item turned off Rally started with no window
and no item at all. Coalescing returned any in-flight request, so the refresh
after starting a suggestion could republish the suggestion that had just been
consumed, and the next click on it would be refused by the version check with
nothing on screen explaining it. If registering the login item succeeded but
writing its marker failed, `initialize` threw before reading the state back and
Settings then offered to turn on something macOS already held on. And a title
with an emoji could be cut through a surrogate pair, rendering `�`.

**Considered and rejected:** for the first three, a mutex around the whole store.
It serializes reads that have no reason to wait on each other and still would not
answer the real question, which is not "is something running" but "is what came
back still about the world it was asked about" — a generation answers that
directly. For the last, trimming a trailing lone surrogate after slicing: it
fixes the rendering and still cuts inside a grapheme cluster, so a flag or a
skin-toned emoji loses its modifier instead.

**Consequences:** `generation` is now the discipline for anything that publishes
into the cache — a new writer that skips the check reintroduces the leak, and a
new invalidation point that does not bump it reintroduces the stale republish.
`present()` and `enabled()` are different questions and must not be conflated.
`menuBarLabel` constructs one module-level `Intl.Segmenter`; a per-call one would
be a real cost on a menu that rebuilds on every content change.

### 2026-08-11 — Every group renders, and an empty one says how it fills

**What changed:** **Suggestions** now behaves like the other two: with nothing to
suggest it keeps its header over **Connect platforms to get daily suggestions on
work streams to create**, instead of disappearing. This reverses the second half
of the entry below, which had just made "Suggestions goes when empty" an
invariant. All three groups are now built by one `pushGroup` helper that takes
the rows and the line to show instead of none. Signing out is the only thing that
removes a group.

**Why:** The reasoning that kept **Pinned** applies here at least as strongly.
An account with no connectors has nothing to suggest *from*, and that is not an

to load.

**Considered and rejected:** the invariant written an hour earlier —
"**Suggestions** has nothing useful to say, so it goes". It was wrong about the

### 2026-08-11 — The empty Pinned section stays, and says how to fill it

**What changed:** Reverses the omission decided in the entry below, on the same
day. With nothing pinned, **Pinned** keeps its header over one disabled row
reading **Pin a work stream to see it here**. Signed out is now the only state
that drops the group.

**Why:** The earlier entry treated an empty section as two wasted rows for the
majority who have never pinned anything. That is the wrong way round: those are
exactly the people who do not know pinning exists, and a section that is simply
absent cannot tell them. The two rows buy the feature its only discovery surface
outside a right-click menu.

**Considered and rejected:** making the row clickable — opening the sidebar, or
pinning the frontmost work stream. Both invent an action the copy does not
promise, and a menu row that does something other than what it says is worse
than one that does nothing.

**Consequences:** the menu now has a fixed floor of rows whatever the account
holds, which is the shape to keep — **Suggestions** stays the exception because
it has nothing to say when empty, not because empty groups are dropped by rule.
*(Overturned the same day by the entry above: it did have something to say.)*

### 2026-08-11 — A Pinned section below Recent

**What changed:** A **Pinned** group under **Recent**, holding the top five of
the reader's own pinned arrangement, from the same `GET /workstreams` response.
Omitted whole when nothing is pinned — reversed the same day by the entry above.

**Why:** Pinning landed on `main` the same day (#95) and gave people a place to
put the work streams they return to. Recency is what moved today; a pin is a
standing choice, and the menu had no way to reach one that had gone quiet enough
to fall off the recent five — which is the case pinning exists for.

**Considered and rejected:** a second request for the pinned list. `GET
/workstreams` already appends every pin to the first page precisely so a quiet
one is not lost to paging, so the page the menu already fetches carries both. The
store partitions on `pinPosition` rather than asking twice.

**Consequences:** `recents` now means *unpinned* recents, because the server
excludes pins from the recency order — a pinned work stream appears in the menu
once, under **Pinned**, exactly as it does in the sidebar. The five-pin display
limit here must not grow into a cap on pinning: `pinning.md` records
two attempts at a real limit and why both failed.

### 2026-08-11 — The suggestions get a group of their own, and both lists get a section header

**What changed:** A separator after **New Automation**, so what Rally suggests
is its own group between what a person can always start and what they have
already started. With no suggestions the group and both its rules collapse to the
single rule that was there before. A **Suggestions** header sits over the
suggestion rows and a **Recent** header over the recent work streams, drawn with
`type: 'header'`. Below macOS 14, which has no such item, they fall back to
disabled rows.

**Why:** The three fixed actions and the suggestion rows ran together as one
block, which read as though the suggestions were more fixed actions rather than
something Rally proposed today. With a rule but no label, neither group said
what it was — a suggested prompt and a work-stream title are both one line of
sentence case, so the lower half of the menu read as one undifferentiated list
of things that already exist.

**Considered and rejected:** disabled rows everywhere, skipping the version
check. They are visually close and one fewer branch, but on the macOS this ships
to they are demonstrably wrong: AppKit gives a real section header its own type
scale and spacing, and the menu is the one surface here people compare directly
against the system's own extras.

**Consequences:** The menu now has a variable number of separators. Anything
adding a group here has to collapse its own rules when it is empty — the rule
belongs to the group, not to the position — and a test asserts no two rules ever
land next to each other for any content. `sectionHeaders` is resolved once at
construction from `process.getSystemVersion()` rather than per rebuild, so it
will not follow a macOS upgrade until Rally restarts — acceptable, since the
upgrade restarts the machine anyway. The **Recent** header is deliberately kept
over the empty state; a future change that hides it there also has to say why
the row below it is not a stray.

### 2026-08-11 — New Work Stream returns to the menu; the login item moves to Settings

**What changed:** **New Work Stream** sits between **New Meeting/Note** and
**New Automation**, reached by a new `avalon://workstreams/new` link. The
**Launch at login** checkbox is gone from the menu; the preference is now
Application → Startup → **Open Rally at login** in Settings. Long suggestion and
work-stream labels truncate at a word boundary instead of mid-word.

**Why:** The first shape of this menu replaced **New Work Stream** with **New
Meeting/Note** rather than adding it, which left the menu unable to start the
thing Rally is mostly for — every suggestion row creates a work stream, but
there was no way to start an empty one. The login-item checkbox was the wrong
control in the wrong place for a second reason: the menu is rebuilt when its
*content* changes, while macOS can turn the login item off from System Settings
whenever it likes, so the checkbox could sit there stale with nothing to correct
it. Settings reads the value from the operating system every time it opens.
Truncation was already there at 60 characters but cut mid-word, and a row reading
"Prepare the Acme cli…" reads as a bug rather than an abbreviation.

**Considered and rejected:** rebuilding the menu on every open so a login
checkbox could stay honest. That means either a synchronous read of the login
item on the click path or a menu that is not ready when it opens, and it buys one
control that has a better home. Also rejected: an ellipsis in the middle of the
label. It keeps the end of a title, which for a model-written prompt is the least
informative part.

**Consequences:** `avalon://workstreams/new` has to be matched before the
identifier branch in both `emitDeepLink` and `app-session.tsx`, or `/new` is
measured against the UUID pattern and rejected. The menu now holds no control for
state the operating system owns independently, and it should stay that way while
it is rebuilt on content changes. `MENU_BAR_LABEL_WORD_BOUNDARY_FLOOR` is a
readability judgement, not a measurement — a shorter menu would want it moved
with the limit.
