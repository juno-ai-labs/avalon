# Menu bar item

Avalon puts a status item in the macOS menu bar. Clicking it drops down a menu
that starts a meeting or note, a work stream, or an automation, starts whatever
Avalon is currently suggesting, and reopens any of the five most recent work
streams or the top five of the reader's own pinned arrangement — plus the two
controls that keep the app reachable when nothing else is on screen: open
Avalon, and quit.

It is the one Avalon surface that outlives every window. Avalon registers itself
to open at login by default and, on a login launch, opens **no** window at all,
so on a freshly started Mac the menu bar item is the whole application until
someone asks for more. That is why nothing here is fetched through a renderer:
the main process holds the menu's content itself.

## Where the code lives

| Path | Responsibility |
| --- | --- |

| `apps/desktop/src/main/menu-bar-content.ts` | The menu's data — recent work streams and suggested work streams — fetched from the regional API by the main process, cached, and started on click. |
| `apps/desktop/src/main/menu-bar.ts` | The status item's lifecycle: whether it exists, and rebuilding its menu when its content moves. |
| `apps/desktop/src/main/launch-at-login.ts` | Whether Avalon is registered to open at login, and `launchedAtLogin`, which decides whether this launch opens a window. |
| `apps/desktop/src/renderer/lib/app-session.tsx` | Where each `avalon://` row lands, including `workstreams/new`. |
| `apps/desktop/src/main/index.ts` | Wires them together: creates the Electron `Tray`, performs the authorized requests (`avalonApiRequest`), and supplies every action. |
| `apps/desktop/src/main/application-settings.ts` | Stores `menuBarEnabled` and `launchAtLoginDefaultApplied` beside Lockdown mode and the Developer preference. |

| `apps/desktop/src/renderer/screens/workspace-settings.tsx` | Application → Appearance → **Show Avalon in the menu bar**, above the app-icon picker, and Application → Startup → **Open Avalon at login**. |

## How it works

### The item

`MenuBarController` reads `menuBarEnabled` at launch and creates an Electron
`Tray` when it is on. The image is a macOS **template image**: black pixels plus
an alpha mask, which AppKit recolors for whichever menu bar it is drawn into.
That is the only treatment that stays legible on macOS 26 and 27, where the menu
bar is translucent and the desktop picture shows through it, and it is also what
makes the item follow light mode, dark mode, and a highlighted item without any
appearance handling of Avalon's own. The filename's `Template` suffix sets this,
and `setTemplateImage(true)` says it again so a rename cannot quietly turn the
mark into a black blob. `nativeImage` resolves the `@2x` sibling by name.

### The menu

The drop-down is rebuilt from `menuBarMenuTemplate` whenever the content or the
preference changes — never on open. A click therefore
always produces a menu immediately. In order:

1. **New Meeting/Note** — opens a meeting-notes window.
2. **New Work Stream** — `avalon://workstreams/new`.
3. **New Automation** — `avalon://automations/new`.
4. A separator.
5. A **Suggestions** header, one row per suggested work stream from
   `GET /work-opportunities`, then another separator. With nothing to suggest,
   one disabled row reads **Connect platforms to get daily suggestions on work
   streams to create** — with no connector there is nothing to suggest *from*,
   and naming that is the difference between a section that looks unstarted and
   one that looks broken.
6. A **Recent** header, then the five most recent work streams from
   `GET /workstreams?limit=5`, which the API already orders by
   `last_activity_at` descending. When there are none, one disabled row says
   whether that is because there is nothing to show or because nobody is signed
   in; the header stays, which is what makes that row read as an answer rather
   than a stray disabled item.
7. A separator, a **Pinned** header, and the top five of the reader's own
   arrangement, from the same response. With nothing pinned the section stays and
   one disabled row says **Pin a work stream to see it here** — most people have
   never pinned anything, and a section that is simply absent teaches them
   nothing about a feature they have not found.

Signed out, **Suggestions** and **Pinned** are dropped whole. Neither has
anything to say to a stranger, and the one message that state needs is already on
the **Recent** row. Everything else renders whether or not it has content, so the
menu has a fixed shape a person can learn.
8. A separator, then **Open Avalon** and **Quit Avalon**.

Both headers use `type: 'header'`, which macOS added in 14 and which AppKit
styles as a real section header. `supportsSectionHeaders` reads
`process.getSystemVersion()` and falls back to a disabled row below that —
unclickable either way, because a header that could be activated is a menu row
that does nothing.

Both list sections carry labels somebody's model wrote, and both contracts allow
180 characters. A macOS menu is as wide as its widest row, so `menuBarLabel`
collapses whitespace and truncates at 60 characters, trimming back to the last
whole word when one falls within the final 20 and cutting hard otherwise —
"Prepare the Acme cli…" is worse than losing the word. Punctuation left dangling
by the cut is dropped, and the ellipsis fits inside the limit rather than pushing
past it.

**The menu carries no login-item control.** It is rebuilt only when its content
moves, and macOS can change the login item from System Settings at any time, so a
checkbox here would go stale with nothing to correct it. Settings owns that
preference and reads it fresh — see below.

Every row that opens something re-enters through the existing `avalon://` deep
links rather than through a second navigation path, so a menu row and a link
clicked anywhere else land in the same place. Starting a suggestion is the one
exception: `POST /work-opportunities/:id/start` runs in the main process first,
and the work stream it creates is then opened by deep link.

`workstreams/new` is the one link added for this menu; the rest already existed.
Rows carry `app.focus({ steal: true })` before they act. A status-item click does
not activate the application the way a Dock click does, so a window opened
without it appears behind whatever is frontmost.

### The content

One request answers both work-stream sections. `GET /workstreams` leaves pins out
of the recency order and appends every one of them to the first page, so a page
of five carries the five most recent *unpinned* streams and the whole pinned list
behind them — [`workstream-pinning.md`](workstream-pinning.md) owns that
behaviour. The store partitions on `pinPosition`, sorts the pinned half by it,
and takes five from each.

`MenuBarContentStore` fetches both halves through `avalonApiRequest`, the main
process's authorized request helper, which renews once through the shared
coalescing refresh on a 401 and always settles. Refreshes happen when the pointer
reaches the status item — `mouse-enter`, and `click` for a keyboard or
accessibility activation — throttled by `refreshIfStale` so a pointer crossing
the menu bar is not a request; when a session is signed in or out; and once at
launch when a credential is already on disk.

### Opening at login

`LaunchAtLoginController` registers Avalon with `app.setLoginItemSettings({
openAtLogin: true })`, which is `SMAppService.mainApp` on macOS 13 and later. The
registration is made once, on the first packaged launch that finds
`launchAtLoginDefaultApplied` unset, and the marker is written only after the
registration succeeds.

**macOS, not `application-settings.json`, owns whether Avalon opens at login.**
Someone can remove the item in System Settings → General → Login Items, and a
preference file that disagreed would put it back unasked. The file records only
that the default has been spent. The controller reads `openAtLogin` back after
every write, because macOS can hold a registration in `requires-approval` until
the person allows it, and Settings has to show what is true rather than what was
asked for.

The toggle lives in Application → **Startup**, and only there. Its state comes
from `DesktopApplicationSettings.launchAtLogin`, which the main process fills
from the operating system on every read.

### Detecting a login launch

`launchedAtLogin` answers the question the whole hidden-launch behavior rests on,
and macOS answers it directly: `app.getLoginItemSettings().wasOpenedAtLogin` is
set on a launch that came from a login item, and unset when a person opened
Avalon from the Dock, Finder, Spotlight, or a deep link. `--hidden` is honoured
alongside it, which is how the path is exercised without waiting for a real
login.

Nothing distinguishes a login from a restart — both are one login event to macOS
— and Avalon treats them the same. When the flag is set **and a status item is
actually in the menu bar**, `whenReady` skips `createMainWindow` entirely. The
second half matters: the item is off whenever someone turned it off, and absent
whenever creating it failed, and hiding into a menu bar item that does not exist
leaves Avalon running with nothing on screen. `MenuBarController.present()` is
that question, and it is deliberately not `enabled()`. `app.on('activate')` still builds a window when the
Dock icon is clicked, and a deep link still builds one on the way to its
destination, so the hidden state is not sticky.

## Invariants

- **The main process, not a renderer, owns the menu's content.** A launch at
  login has no window, so anything that asked a renderer for the recent list
  would show an empty menu exactly when the menu is the only surface there is.
- **The menu is built from cache, never fetched on open.** A drop-down that
  waited on the network would hang under the pointer on a bad connection.
- **Signing out clears the cache, including whatever is still on the wire.**
  The previous account's work-stream titles are workspace content, and a request
  issued before the sign-out would otherwise land afterwards and put them back.
  Every published answer carries the `generation` it was fetched under and is
  dropped if that is no longer current. Anything that adds a new way to publish
  has to carry the same check.
- **A launch opens no window only when there is a status item to hide into.**
  Otherwise Avalon starts invisible with no menu bar presence, reachable only by
  hunting for it in the Dock.
- **The `Template` filename suffix and `@2x` sibling are load-bearing.** Losing
  the suffix gives a black square on a dark menu bar; losing the `@2x` file gives
  a blurred mark on every Retina Mac. Neither fails a build, so
  `verify-macos-app.mjs` checks both are in the bundle.
- **`menuBarEnabled` reads as on when it is missing or unreadable.** The item
  ships on, and any other reading would silently withdraw it from every device
  that upgraded.
- **Every group renders, and an empty one says how it fills.** All three go
  through `pushGroup`, which takes the rows and the line to show instead of
  none, so a group cannot be added that renders a bare header or vanishes
  silently. Signing out is the only thing that removes a group, and only
  **Suggestions** and **Pinned**.
- **The menu never renders state the operating system can change behind it.**
  It is rebuilt on content changes, not on open, so anything macOS owns
  independently — the login item is the case that came up — belongs in Settings,
  which reads fresh.
- **A development build never registers a login item by default.** Its executable
  is a shared Electron binary in `node_modules` that would outlive the checkout.
  The toggle still works; only the automatic registration is withheld.
- **A failed status item is a degraded menu bar, not a failed launch.** Every
  action the menu offers also exists inside the app.

## Boundary

This module owns the status item, its menu, the data behind that menu, and the
login-item registration. It exposes two IPC channels —
`application-settings:set-menu-bar-enabled` and
`application-settings:set-launch-at-login` — and four fields on
`DesktopApplicationSettings`: `menuBarEnabled`, `menuBarAvailable`,
`launchAtLogin`, and `launchAtLoginAvailable`.

It does **not** own: the application menu bar at the top of the screen
(`application-menu.ts`), the Dock and Finder icon
([`DESKTOP_ICONS.md`](DESKTOP_ICONS.md)), how a suggestion is generated or ranked
([`SUGGESTED_WORK.md`](SUGGESTED_WORK.md)), what a work-stream link means
([`WORKSTREAM_LINKS.md`](WORKSTREAM_LINKS.md)), or session storage and refresh —
it borrows `loadStoredAuth` and the coalescing refresh and adds nothing to them.

It depends on the `avalon://` deep-link vocabulary already handled in
`app-session.tsx`. Adding a menu row that navigates somewhere new means adding
the link there first, not a second navigation channel here.

## Failure modes and limits

| Situation | Behavior |
| --- | --- |
| One half of a refresh fails | The other half is published and the stale half is kept. The recent list is what a person navigates with; a failing suggestion poll must not take it down. |
| Both halves fail | The last good menu stays. A warning is logged once per attempt. |
| Signed out | All three fixed actions remain; the recent section becomes one disabled **Sign in to Avalon** row. Content refreshes are skipped entirely rather than failing twice per pointer arrival. |
| A label runs long | Truncated to 60 characters at the last word boundary in the final 20, hard otherwise. |
| Nothing to suggest | The header stays over one disabled row naming what has to happen first: **Connect platforms to get daily suggestions on work streams to create**. |
| Nothing pinned | The header stays over one disabled row: **Pin a work stream to see it here**. |
| Signed out | **Suggestions** and **Pinned** are dropped entirely, headers and rules included; **Recent** carries the sign-in row. |
| More than five pins | The top five of the arrangement are shown. This is a display limit on a menu, not a cap on pinning — see the invariant in [`workstream-pinning.md`](workstream-pinning.md) about nothing counting pins against a limit. |
| macOS 13 or older | Both headers fall back to disabled rows. Everything else is unchanged. |
| A request hangs | Aborted after 8 s (`MENU_BAR_REQUEST_TIMEOUT_MS`). A wedged request would otherwise freeze the content for the life of the process. |
| Sign-out, or a suggestion started, while a refresh is in flight | The generation moves, so that answer is discarded on arrival and a caller asking again gets a new request rather than the superseded one. |
| The login item registers but the marker fails to write | The registration is reported as it stands, not as off. The marker is retried on the next launch. |
| Starting a suggestion fails | The main window is opened, where the same suggestion is on the home screen and starting it again reports its own failure. A menu click has to land somewhere. |
| The `Tray` cannot be created | Logged and skipped. The preference stays on, so the next launch tries again. |
| Not macOS | No status item; `menuBarAvailable` is false and Settings omits the toggle. The preference is still stored, so the same profile on a Mac gets the choice rather than the default. |

`menuBarLabel` counts and cuts in **graphemes**, via `Intl.Segmenter` — a title
can carry an emoji, and a cut by UTF-16 code unit leaves a lone surrogate
rendering as `�` in front of the ellipsis. The segmentation is skipped when the
code-unit length already fits, so the ordinary label never pays for it.

The empty-state copy is exempt from `menuBarLabel`'s 60-character limit. That
limit stops one model-written title stretching the menu; the fixed copy is ours,
has to read in full, and sets the menu's width only for an account that has
nothing in the section it belongs to.

Numbers: five recent work streams (`MENU_BAR_RECENT_LIMIT`), five pinned
(`MENU_BAR_PINNED_LIMIT`), at most four
suggestions (what `GET /work-opportunities` returns), 60-character labels
(`MENU_BAR_LABEL_MAX_LENGTH`) with a word boundary honoured from 40
(`MENU_BAR_LABEL_WORD_BOUNDARY_FLOOR`), a 15 s content staleness window
(`MENU_BAR_CONTENT_MAX_AGE_MS`), and an 8 s request timeout.

## Testing

```text
pnpm --filter @avalon/desktop exec vitest run src/main/menu-bar-menu.test.ts \
  src/main/menu-bar-content.test.ts src/main/menu-bar.test.ts \
  src/main/launch-at-login.test.ts
```

Nothing here imports Electron at runtime. `menu-bar-menu.ts` builds a plain
template object, and the other three take their Electron surface as injected
dependencies — `MenuBarTray`, `getLoginItemState`/`setOpenAtLogin`, and
`requestJson`. That is deliberate: the suite has no display server, and a `Tray`
constructed for real would need one.

Two traps. `MenuBarContentStore` takes an injectable `now`, so drive the
staleness window with it rather than with a timer. And the template's `click`
handlers are typed with the menu item, window, and event AppKit passes but ignore
all three, so tests call them through a cast rather than fabricating those
arguments.

The status item itself cannot be verified in the sandbox — see
[`dev-environment.md`](dev-environment.md#what-cannot-be-verified-in-a-sandbox).
What can be, and was: the Settings toggle in a real window, and the hidden launch,
by starting the client with `--hidden` and confirming it has zero renderer
targets while the main process still loads the menu's content.

## Security and trust model

The renderer's only reach into this module is
`application-settings:set-menu-bar-enabled` and
`application-settings:set-launch-at-login`, each of which takes a boolean and is
rejected for anything else. The menu itself is built in the main process from
values the API returned, and its rows carry identifiers the main process fetched
rather than anything a renderer supplied.

`avalonApiRequest` is a new main-process caller of the stored credential. It uses
the same access token and regional endpoint as the feature-flag poll, adds no
credential storage of its own, and reaches only `/workstreams` and
`/work-opportunities`. Work-stream titles are workspace content and are held in
main-process memory only — never written to disk — and are dropped on sign-out.

`menuBarEnabled` and `launchAtLoginDefaultApplied` share
`application-settings.json` with Lockdown mode, so they go through the same
shared write queue: a lost update there would leave an off Lockdown preference
beside a Lockdown envelope, which the next launch reads as an out-of-app edit and
answers by deleting the stored credentials. See [`SECURITY.md`](SECURITY.md).

## Changelog

### 2026-08-11 — Avalon gets a menu bar item, opens at login, and starts hidden

**What changed:** A macOS status item carrying the Avalon mark as a template
image, with a drop-down for a new meeting or note, a new automation, the current
suggestions, and the five most recent work streams. Application → Appearance
gained **Show Avalon in the menu bar**, on by default. Avalon now registers
itself to open at login by default, offers that as a checkbox in the menu, and
opens no window when the launch came from the login item.

**Why:** Everything Avalon can start required finding and raising a window first.
The status item makes the four things people actually start reachable from any
application, and opening at login is what makes it reachable without anyone
having launched Avalon at all — which is only tolerable if that launch is silent,
hence the hidden start.

**Considered and rejected:**

- *Pushing the menu's content from the renderer over IPC.* It is less code and it
  reuses the React Query caches the home screen already has. It also fails in the
  one case that motivated the feature: a login launch has no renderer, so the
  menu would be empty exactly when it is the only surface. Fetching in the main
  process costs a second, narrower API client and is the reason the item works
  with no window open.
- *Parsing the full `WorkstreamSchema` from `@avalon/contracts` for the recent
  list.* The menu reads an id and a title. Parsing the whole contract would let an
  unrelated field addition on the server empty the menu on an older client, so
  `menu-bar-content.ts` keeps its own narrow schemas and ignores everything else.
- *Storing whether Avalon opens at login in `application-settings.json`.* macOS
  lets someone remove the login item from System Settings, and a preference file
  that disagreed would re-register it behind their back. The file records only
  that the enabled-by-default registration has happened.
- *`openAsHidden`.* It is the obvious Electron answer and it does nothing on macOS
  13 and later. `wasOpenedAtLogin` plus skipping `createMainWindow` is what
  actually works.

**Consequences:** The main process now makes API requests of its own, so
`avalonApiRequest` is the place to extend rather than a second ad-hoc `net.fetch`.
The menu's rows go through the existing `avalon://` deep links, so a new row that
navigates somewhere needs that link to exist first. Two resource names are
load-bearing and checked by the package verifier: the `Template` suffix and the
`@2x` sibling. And Avalon can now be running with no window at all — anything
that assumes `mainWindow` exists after startup has to keep handling `null`, which
`sendDeepLink` and `activate` already do.

**Not done:** a submenu for older work streams.

### 2026-08-11 — Five defects found in review of the original build

**What changed:** (1) Cached content now carries a generation, bumped on
sign-out and on starting a suggestion; an answer that arrives under a stale one
is discarded, and `refresh()` no longer hands back an in-flight request issued
under it. (2) A login launch opens a window unless a status item is actually
present, which `MenuBarController.present()` now answers. (3)
`LaunchAtLoginController.initialize` reads the login item back in a `finally`.
(4) `menuBarLabel` cuts in graphemes rather than UTF-16 code units.

**Why:** each was a real failure, none reachable from the tests as written.
Sign-out emptied the cache but not the request already on the wire, so the
previous account's work-stream titles came back into the menu moments later —
the exact leak the method existed to prevent. A login launch checked the
*preference*, so with the menu bar item turned off Avalon started with no window
and no item at all. Coalescing returned any in-flight request, so the refresh
after starting a suggestion could republish the suggestion that had just been
consumed, and the next click on it would be refused by the version check with
nothing on screen explaining it. If registering the login item succeeded but
writing its marker failed, `initialize` threw before reading the state back and
Settings then offered to turn on something macOS already held on. And a title
with an emoji could be cut through a surrogate pair, rendering `�`.

**Considered and rejected:** for the first three, a mutex around the whole store.
It serializes reads that have no reason to wait on each other and still would not
answer the real question, which is not "is something running" but "is what came
back still about the world it was asked about" — a generation answers that
directly. For the last, trimming a trailing lone surrogate after slicing: it
fixes the rendering and still cuts inside a grapheme cluster, so a flag or a
skin-toned emoji loses its modifier instead.

**Consequences:** `generation` is now the discipline for anything that publishes
into the cache — a new writer that skips the check reintroduces the leak, and a
new invalidation point that does not bump it reintroduces the stale republish.
`present()` and `enabled()` are different questions and must not be conflated.
`menuBarLabel` constructs one module-level `Intl.Segmenter`; a per-call one would
be a real cost on a menu that rebuilds on every content change.

### 2026-08-11 — Every group renders, and an empty one says how it fills

**What changed:** **Suggestions** now behaves like the other two: with nothing to
suggest it keeps its header over **Connect platforms to get daily suggestions on
work streams to create**, instead of disappearing. This reverses the second half
of the entry below, which had just made "Suggestions goes when empty" an
invariant. All three groups are now built by one `pushGroup` helper that takes
the rows and the line to show instead of none. Signing out is the only thing that
removes a group.

**Why:** The reasoning that kept **Pinned** applies here at least as strongly.
An account with no connectors has nothing to suggest *from*, and that is not an
absence of news — it is a step nobody has taken. A vanishing section says
neither, and a bare heading with nothing under it reads as a section that failed
to load.

**Considered and rejected:** the invariant written an hour earlier —
"**Suggestions** has nothing useful to say, so it goes". It was wrong about the
one thing that matters: the state is not "no suggestions today", it is "Avalon
has nothing to look at". Also rejected: shortening the copy to fit the
60-character content limit. That limit exists to stop a model-written title
stretching the menu, and applying it to our own sentence would clip the
instruction that is the whole point of the row.

**Consequences:** the menu is now one fixed shape whatever the account holds,
which is worth keeping — a group that renders conditionally makes the rows below
it move, and this menu is used by muscle memory. Adding a group means adding an
empty line for it. The suggestions row is the widest fixed string in the menu and
therefore sets its width for a connector-less account.

### 2026-08-11 — The empty Pinned section stays, and says how to fill it

**What changed:** Reverses the omission decided in the entry below, on the same
day. With nothing pinned, **Pinned** keeps its header over one disabled row
reading **Pin a work stream to see it here**. Signed out is now the only state
that drops the group.

**Why:** The earlier entry treated an empty section as two wasted rows for the

exactly the people who do not know pinning exists, and a section that is simply

**Considered and rejected:** making the row clickable — opening the sidebar, or
pinning the frontmost work stream. Both invent an action the copy does not
promise, and a menu row that does something other than what it says is worse
than one that does nothing.

**Consequences:** the menu now has a fixed floor of rows whatever the account
holds, which is the shape to keep — **Suggestions** stays the exception because
it has nothing to say when empty, not because empty groups are dropped by rule.
*(Overturned the same day by the entry above: it did have something to say.)*

### 2026-08-11 — A Pinned section below Recent

**What changed:** A **Pinned** group under **Recent**, holding the top five of
the reader's own pinned arrangement, from the same `GET /workstreams` response.
Omitted whole when nothing is pinned — reversed the same day by the entry above.

**Why:** Pinning landed on `main` the same day (#95) and gave people a place to
put the work streams they return to. Recency is what moved today; a pin is a
standing choice, and the menu had no way to reach one that had gone quiet enough
to fall off the recent five — which is the case pinning exists for.

**Considered and rejected:** a second request for the pinned list. `GET
/workstreams` already appends every pin to the first page precisely so a quiet
one is not lost to paging, so the page the menu already fetches carries both. The
store partitions on `pinPosition` rather than asking twice.

**Consequences:** `recents` now means *unpinned* recents, because the server
excludes pins from the recency order — a pinned work stream appears in the menu
once, under **Pinned**, exactly as it does in the sidebar. The five-pin display
limit here must not grow into a cap on pinning: `workstream-pinning.md` records
two attempts at a real limit and why both failed.

### 2026-08-11 — Both lists get a section header

**What changed:** A **Suggestions** header over the suggestion rows and a
**Recent** header over the recent work streams, drawn with `type: 'header'`.
Below macOS 14, which has no such item, they fall back to disabled rows.

**Why:** With a rule but no label, neither group said what it was — a suggested
prompt and a work-stream title are both one line of sentence case, so the lower
half of the menu read as one undifferentiated list of things that already exist.

**Considered and rejected:** disabled rows everywhere, skipping the version
check. They are visually close and one fewer branch, but on the macOS this ships
to they are demonstrably wrong: AppKit gives a real section header its own type
scale and spacing, and the menu is the one surface here people compare directly
against the system's own extras.

**Consequences:** `sectionHeaders` is resolved once at construction from
`process.getSystemVersion()` rather than per rebuild, so it will not follow a
macOS upgrade until Avalon restarts — acceptable, since the upgrade restarts the
machine anyway. The **Recent** header is deliberately kept over the empty state;
a future change that hides it there also has to say why the row below it is not a
stray.

### 2026-08-11 — The suggestions get a group of their own

**What changed:** A separator after **New Automation**, so what Avalon suggests
is its own group between what a person can always start and what they have
already started. With no suggestions the group and both its rules collapse to the
single rule that was there before.

**Why:** The three fixed actions and the suggestion rows ran together as one
block, which read as though the suggestions were more fixed actions rather than
something Avalon proposed today.

**Consequences:** The menu now has a variable number of separators. Anything
adding a group here has to collapse its own rules when it is empty — the rule
belongs to the group, not to the position — and a test asserts no two rules ever
land next to each other for any content.

**What changed:** **New Work Stream** sits between **New Meeting/Note** and
**New Automation**, reached by a new `avalon://workstreams/new` link. The
**Launch at login** checkbox is gone from the menu; the preference is now
Application → Startup → **Open Avalon at login** in Settings. Long suggestion and
work-stream labels truncate at a word boundary instead of mid-word.

**Why:** The first shape of this menu replaced **New Work Stream** with **New
Meeting/Note** rather than adding it, which left the menu unable to start the
thing Avalon is mostly for — every suggestion row creates a work stream, but
there was no way to start an empty one. The login-item checkbox was the wrong
control in the wrong place for a second reason: the menu is rebuilt when its
*content* changes, while macOS can turn the login item off from System Settings
whenever it likes, so the checkbox could sit there stale with nothing to correct
it. Settings reads the value from the operating system every time it opens.
Truncation was already there at 60 characters but cut mid-word, and a row reading
"Prepare the Acme cli…" reads as a bug rather than an abbreviation.

**Considered and rejected:** rebuilding the menu on every open so a login
checkbox could stay honest. That means either a synchronous read of the login
item on the click path or a menu that is not ready when it opens, and it buys one
control that has a better home. Also rejected: an ellipsis in the middle of the
label. It keeps the end of a title, which for a model-written prompt is the least
informative part.

**Consequences:** `avalon://workstreams/new` has to be matched before the
identifier branch in both `emitDeepLink` and `app-session.tsx`, or `/new` is
measured against the UUID pattern and rejected. The menu now holds no control for
state the operating system owns independently, and it should stay that way while
it is rebuilt on content changes. `MENU_BAR_LABEL_WORD_BOUNDARY_FLOOR` is a
readability judgement, not a measurement — a shorter menu would want it moved
with the limit.
