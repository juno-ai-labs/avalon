# Assumptions

These choices resolve low-level ambiguity without changing the product contract.

1. The prototype uses one workspace per initial Google-authenticated user. Invitations and additional memberships are supported by the schema/API, but workspace switching is deferred.
2. Global and EU deployments run identical code with separate bindings. Local development uses one emulated region at a time and a header-gated development identity only when `AVALON_DEV_AUTH=true`.
3. The Hono API is the only public application backend. Electron loads a bundled renderer and never loads an arbitrary hosted page into its privileged window.
4. UUIDv7 identifiers are generated at the service boundary for sortable uniqueness.
5. D1 stores searchable metadata and complete short text messages. R2 stores uploads, large connector payloads, snapshots, and artifacts.
6. OpenRouter model names are configuration, with conservative defaults documented in `.env.example`; no model selector appears in product UI.
7. Google APIs are implemented directly over their documented REST endpoints so connector behavior remains Worker-compatible and the dependency surface stays small.
8. A development seed is explicit and test-only. Production startup never creates demo records and the desktop does not silently fall back to hardcoded data.
9. The supplied screenshots define density, proportions, typography, color, transcript alignment, run-history treatment, and right-rail behavior. Their product-specific labels are examples, not data to hardcode into production.
10. The contextual right rail is 360px by default, hidden on initial work-stream entry, resizable from 320–560px, and becomes an accessible overlay below 960px. Its active content can be `People & resources`, `Background tasks`, or `Run history` according to the current screen.
11. Background-task cards are derived from persisted harness/tool events. Transcript links focus the corresponding event; they do not open a second chat abstraction.
12. The provided `.env.local` remains untracked. Existing keys are preserved. Missing provider credentials produce explicit setup errors while their complete integration paths remain testable with fixtures.
13. Cloudflare resource creation/deployment is attempted only after local verification and only when the supplied account credentials satisfy Wrangler authentication. No existing named resource is deleted or replaced.
14. “Packageable Electron application” means a reproducible platform build configuration and successful unpacked packaging on the current host; code-signing/notarization credentials are outside the prototype prerequisites.
15. Application → Developer → **Debug enabled** is a per-device preference stored beside Lockdown mode in `application-settings.json`, not workspace state, because it describes how this installation behaves rather than what the workspace is. Its menu entries follow the product's spelling — **Copy work stream id** and **Copy automation id** — and sit with the non-destructive actions, above the separator that isolates Archive. The same preference decides how much of the right rail's **Details** section is shown: with debugging off it carries only the rows that describe the work stream to a person — Email where the work stream has an address, then Created by, Created, and Last activity — and everything that describes how the work stream is wired (origin, automation subscription, planned time, harness run, and the identifiers) appears only when debugging is on. The address itself is clipped to one line in both states, because it is a value people copy rather than read; the preference decides which rows exist, never how one of them is laid out.
16. The transcript reads as people on one side and Avalon on the other: every person-authored turn sits on the right — the signed-in person's, a coworker's, and one relayed in by a connector on someone's behalf — while Avalon keeps the full-width left column. Who sent it is carried by the header above the bubble (accent dot, name, and for a relayed turn its source), never by which side it is on, so a turn does not change position when the person who wrote it is not the person reading. This refines item 9: where a supplied screenshot shows a coworker's turn on the left, the rule above wins.
17. The right sidebar holds one panel at a time: HyperSight or the context inspector, never both. Opening either closes the other, and every header control that owns the sidebar — HyperSight, Work-stream context, Background tasks — reads as pressed while its own panel is showing and closes it again from that state. HyperSight's visibility is the personal per-work-stream preference the API already stores, so yielding the sidebar to the inspector is written back the same way the toggle is and the next visit opens where the last one left off. Widths are the exception to that sharing: each panel remembers its own width per work stream on the device, both starting at 360px in a work stream that has never opened them, so a wide HyperSight in one stream never narrows the inspector in another. Both are resized by the same short handle on the sidebar's leading edge, which colors and grows under the pointer rather than drawing a second border down the panel.
18. A scheduled digest run executes in a work stream marked `system_kind`, rather than in no work stream at all. The agent loop is work-stream shaped end to end — the transcript is `messages`, and compaction, tool invocations, artifacts, and the realtime room all key off `workstream_id` — so a genuinely work-stream-less run would be a second loop rather than the one every other scheduled run uses. Marking it instead reuses that whole abstraction. Visibility and listing are separate questions: only an active participant may read one, which for a digest is its recipient alone, while whether it appears in the sidebar is off by default and turned on by Application → Developer → **Debug enabled**, where it renders dimmed and gear-marked one level below ordinary work. One is created per person rather than per run, so nothing accumulates and a later digest can see what earlier ones already said. The column is deliberately general: any future internal agent surface marks itself the same way rather than inventing a second mechanism.
