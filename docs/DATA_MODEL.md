# Data model

The checked-in D1 migration is authoritative. Application contracts expose camel-cased TypeScript values; storage uses explicit snake-cased columns and JSON only where provider- or model-shaped data is not relationally queried.

## Identity and tenancy

- `users` stores Google identity subjects and display information.
- `workspaces` pins an immutable `global` or `eu` region.
- `workspace_members` authorizes users as owner, admin, or member.
- `sessions`, `oauth_states`, and `desktop_login_tickets` support revocable sessions, PKCE, and single-use Electron deep-link completion.
- `workspace_invitations` supports explicit membership growth without introducing a workspace switcher in V1.

Every tenant-owned table carries `workspace_id`, and every repository lookup includes it. Knowing an object ID is never sufficient authorization.

## Work streams

- `workstreams` is the central object. `origin_type` distinguishes ad hoc work from automation output without splitting the UI. `objective` is the work stream's description; `description_source` records whether a person wrote it (`authored`) or it was derived at creation or by the refresh loop (`derived`), which is what lets an automatic rewrite weigh a deliberate line differently from a copied opening message. `title_status` is the same question for the title: `naming` while the naming agent is choosing the first one and the stored title is a placeholder clients render as a skeleton, `automatic` once Avalon has named it and one later pass may still replace it, `settled` when a person named it, a caller supplied it, or that pass has run.
- `workstream_description_refreshes` holds one row per work stream: the last evaluation by the loop that rewrites a description once the work stream's purpose has moved. `rest_until` is both the admission clock and the single-writer claim — it is pushed forward when an evaluation starts, so two runs finishing together cannot both spend a window and a failing model is not retried by every run behind it. It stores the resolved instant rather than the inputs because the rest is earned: `consecutive_keeps` doubles it to a ceiling, a rewrite returns it to the floor, and a person editing the description buys a full rest outright. `decision` records the outcome including `kept`, because knowing the loop looked is what separates a description that still fits from one nothing has examined. See [`workstream-descriptions.md`](workstream-descriptions.md).
- `workstreams.scope` answers who may read a work stream, in the same `personal`/`workspace` vocabulary `notes.scope` uses. `personal` is enforced as "an active participant, and nobody else" by both the list query and the single-row read, so privacy is a declared property of the row rather than a rule each caller has to remember. Existing rows are `workspace`; the one narrower rule already in the code — a personal automation's work stream being visible to its owner — stays separate, because those rows carry no participants and reading them as `personal` would hide them from the person they belong to. The rule itself is written once, in `apps/api/src/lib/workstream-visibility.ts`, and parameterized by the SQL expression naming the reader so the work-stream room can bind by position and its eviction sweep can ask it of a whole column; a call site that pastes the rule instead of importing it is how it lost `scope` before.
- **A work stream moves between the two, and privacy is not ownership.** `PATCH /workstreams/:id` takes `scope`, and the sidebar's right-click menu offers it as **Make private** / **Make public to workspace**, named for the state it moves to the way the note item is. Anyone who may read a work stream may move it either way, and everyone left inside a private one can read it, write to it, and add anyone else in the workspace — `addParticipant` requires only that the caller can read the work stream and that the person named is an active member. Two consequences fall out of `personal` being enforced against participants: whoever makes a work stream private is upserted as one in the same batch as the scope itself — either both land or neither does, and a person the upsert genuinely adds is announced as a participant — or the one action that closes a work stream would be the one that locks its author out of it; and the change has to reach the sockets already inside the room, which authorized once at connect time. The room evicts the connections that may no longer read it and sends `workstream_scope_changed` to the rest. Two kinds of row refuse the change with `scope_change_unsupported`, because `scope` is not what decides who reads them: a `system_kind` row is machinery assembled from one person's activity, and an automation-generated row takes its audience from that automation's scope — opening it would broaden nothing and closing it would hide it from the owner, who reaches it by owning the automation rather than by being a participant.
- `workstreams.system_kind` is the different question of whether a work stream is *machinery*. `NULL` is ordinary work; any non-`NULL` value (`digest` today) is a subsystem's own work stream, so an internal run can reuse the whole agent loop rather than inventing a second one. It decides whether the row is *listed* — off unless the caller passes `includeSystem`, which the desktop does when Debug enabled is on — never who may read it. A digest's work stream carries both: `scope = 'personal'` and `system_kind = 'digest'`. See [`DIGESTS.md`](DIGESTS.md).
- `workstreams.model_override` pins this one work stream's runs to an OpenRouter model, ahead of the `agent-model-workstream` flag. `NULL` — the overwhelming majority — means the flag decides. It exists because model *selection* is a fleet-wide rollout and this is the opposite question, asked about one piece of work at the moment it is created; see [`FEATURE_FLAGS.md`](FEATURE_FLAGS.md#a-work-streams-own-model). The column carries no `CHECK` enumerating the ids: the selectable set is a product decision that moves, so it lives in `AGENT_MODEL_OVERRIDES` and is re-validated on read, which lets a model be retired without a migration.
- `workstream_pins` is one person's pinned work streams and the order they arranged them in — keyed `(workstream_id, user_id)` like `workstream_read_states`, and for the same reason: a pin is one person's opinion about a shared row, so it cannot be a column on `workstreams` without imposing one member's arrangement on the workspace. `position` is unique and ascending per person and is rewritten as a dense run by every unpin and reorder, because a tie leaves "what order is this list in" without a single answer; a new pin takes `MAX(position) + 1` rather than the row count, so two pins made at once — or one made after a cascade delete left a hole — cannot land on the same number. It is deliberately not uniquely indexed, since any intermediate state of the rewrite collides with itself. A pin is never broadcast — it changes nothing anyone else can see — and it never widens what its owner may read: every pinned read still applies the visibility rule above, so a pin left behind by a work stream that was archived or narrowed contributes no row while remaining removable by its owner. See [`workstream-pinning.md`](workstream-pinning.md).
- `workstream_participants` records explicit participation reasons. Viewer presence is intentionally absent from D1.
- `messages` has a per-work-stream `sequence_number`; `workstreams.next_sequence_number` allocates ordered events.
- `message_mentions` stores validated person and connector spans.
- `resources` holds metadata while `content_ref` points at the immutable, user-visible original in regional R2. Image attachments may also carry a `model_content_ref`, `model_mime_type`, SHA-256, and bounded model metadata for a signature-validated derivative used only for model input. Animated GIF metadata records dimensions, frame count, duration, approximate frame rate, loop behavior, and storyboard timestamps. `workstream_resources` owns attachment/watch behavior.
- `artifacts`, `elicitations`, and `activity_suggestions` are first-class transcript blocks.

## Automations and execution

- `automation_templates` and immutable `automation_template_versions` separate shared behavior from credentials. The one exception to that immutability is a draft's own version, which the compiler rewrites in place on every turn rather than leaving twenty versions behind for a template nobody has run; it is safe only because a draft's template is `private` and cannot be shared until the automation is created, so nothing else is ever pinned to that row. `AutomationService.draftVersionUpdate` is the only writer, and it takes a required condition bounding it to a version its own subscription still pins — see [`automation-drafts.md`](automation-drafts.md).
- `automation_subscriptions` pins one version and owns scope, principal, connector bindings, activity-source bindings, overrides, and schedule state. `connector_bindings_json` maps model-facing plugin IDs to frozen connection IDs; `activity_trigger_bindings_json` independently maps reusable trigger source slots to those plugin IDs so an activity can match only the selected installation. `status` is the run state (`draft`, `active`, `paused`, `error`); `lifecycle_state` is the separate question of whether the subscription is still present (`visible`, `archived`, `deleted`), so a dismissed draft and a deleted automation share one enum instead of a flag each, and `updated_at` records when the transition happened. A `draft` row is an automation someone is still setting up: the compiler writes one on its first turn and updates it on every turn after, `draft_conversation_json` holds the conversation so it can be picked back up, and creating the automation promotes that same row to `active` and clears the column rather than inserting a second one — [`automation-drafts.md`](automation-drafts.md) owns that lifecycle and the reasons a draft carries no schedule, no address, and no workspace scope. Archiving is restricted to drafts; deleting is allowed at any status and also disables the schedules and the email route. A deleted row is kept, never removed: automation runs, generated work streams, the memory scope, and the permanent email tombstone all reference it. Every path that starts a run — scheduler alarm, activity matching, inbound email — requires `status = 'active' AND lifecycle_state = 'visible'`, so a hidden automation cannot run. `model_override` is the same pin as the work-stream column above, held here because the runs it applies to do not exist yet; every path that creates a run copies it onto the work stream it creates rather than joining back, so a run reads its model from its own row and a run that already happened keeps describing the model it was pinned to. Three separate places build that row — `AutomationService.createRun`, the workspace scheduler's `startAutomation`, and the activity consumer's `startActivityAutomation` — so a column added to one and not the others is honoured by manual runs while scheduled and activity-triggered runs silently ignore it.
- `memory_scopes` owns durable work-stream, automation, user, and workspace memory authority. `memory_items` stores compact prose facts; `memory_tables`, `memory_table_columns`, `memory_table_rows`, and `memory_table_cells` store typed collections with natural-key deduplication and targeted queries. Automation template versions declare table schemas, while every subscription owns an independent materialized automation scope and shares it across its generated work streams.
- `automation_runs.workstream_id` is unique, enforcing the one-run/one-work-stream contract.
- The partial unique index on `(automation_subscription_id, planned_for)` converges early-open and alarm-driven scheduled-run creation.
- `harness_runs` records each bounded model loop. `tool_invocations` is unique on `(harness_run_id, tool_call_id)` and stores input hashes plus side-effect state.
- `schedules` is canonical. One workspace Durable Object alarm reads due rows and advances them transactionally/idempotently. Exactly one of `automation_subscription_id`, `connector_connection_id`, and `digest_schedule_id` is set on a row.
- `workstream_wakeups` holds one-shot prompt wake-ups a run scheduled for itself. It is separate from `schedules` because a wake-up is one-shot, belongs to a work stream rather than a subscription or connection, and carries the prompt text that becomes the resulting run's trigger. The same workspace alarm unions it with `schedules` and `resource_watches`. `(workstream_id, idempotency_key)` is unique, so a replayed tool receipt resolves to the wake-up its first attempt created; `status` moves `pending → fired` under a version guard before the run is launched, making a wake-up at-most-once rather than at-least-once.

## Activity log and digests

- `activity_events` is the first-party record of what happened that someone should hear about, separate from the `activities` ingest table below. `audience_kind` stores a visibility *rule* — `workspace`, `user`, or `workstream` — resolved against the reader at read time, so a work stream gaining a participant retroactively gains them its history. `activity_event_targets` is the different question of who an event is *about* (`mentioned`, `involved`, …), which is what lets a consumer lead with it; a target outside the audience is stored but still filtered out on read. `event_type` and `subject_type` are open strings so a producer adds a value rather than a column.
- `activity_events.digestible` is the separate question of whether anybody *wants* to hear about an event, as opposed to who *may*. It is fixed when the row is written — from the connector's manifest for connector activity, at the call site for a first-party producer — because the question is asked far more often than it is answered, and re-deriving it on read would need a manifest that may have changed or that this region does not register. It carries no index: the reads that use it are already anchored on `activity_events_cursor_idx`, and a two-value column ahead of that range would only widen the index for every other reader. Its `DEFAULT 1` is the one part of this that fails open rather than closed, and it is deliberately left that way — it governs only an insert that does not name the column, which no code path does, and changing it now costs a full rebuild of the log with `activity_event_targets` staged around it. [The runbook](RUNBOOK.md#the-window-between-a-migration-and-the-worker-that-needs-it) records what that default cost during the deployment that added it, and why the next such column should pick the fail-closed value up front. [`DIGESTS.md`](DIGESTS.md#digestible-what-a-person-should-be-told) owns the rule.
- `activity_events.log_sequence` is `INTEGER PRIMARY KEY AUTOINCREMENT` and is the only cursor axis. Timestamps cannot order it: two events written in the same millisecond tie, and any tiebreak can place the second below a cursor taken after the first, dropping it permanently. `AUTOINCREMENT` is required rather than incidental — a reused rowid would appear beneath a cursor that has already passed.
- `digest_schedules` is one digest per person per workspace: a `day_mask` (bit 0 Sunday) and a lazily created `system_workstream_id`. Every active member gets one — weekdays at 09:00, by email — created by the cron reconciler rather than at the several places a membership is made. A row is never deleted, so its absence unambiguously means "never had one" and the reconciler cannot resurrect a digest somebody switched off. It deliberately has no timezone column — a digest's times are wall-clock times in its owner's day, and `users.timezone` already answers that; a second copy would disagree the first time somebody moved. The derived `schedules` rows carry the resolved zone and are re-derived when the account timezone changes. `digest_schedule_times` holds the delivery times, and one `schedules` row is derived per *time* — a single RRULE cannot express a list of times, because `BYHOUR` and `BYMINUTE` multiply out.
- `digest_delivery_targets` freezes each destination, with a per-family `CHECK`: `email` carries an address and no connection, and every other type carries a connection plus the frozen provider identity. `target_type` is deliberately not an enum, so a connector declaring a new `userDelivery` surface becomes selectable without a migration.
- `digest_deliveries` is both the idempotency record and the cursor. `(digest_schedule_id, planned_for)` is unique, so a re-fired alarm resolves to the attempt already in flight; `cursor_through` of the newest settled row is where the next digest starts reading. `empty` is a settled outcome, not a failure. Digests never write `workstream_read_states`: a digest cursor is what someone has been *told*, a read waterline is what they have *read*.

## Connectors and activities

- `connector_connections` owns scope, encrypted provider credentials, capabilities, cursors, and health.
- `slack_installation_routes` is the opaque Global team-to-region directory; `slack_user_links`, `slack_agent_sessions`, and durable `slack_ingress_jobs` remain regional.
- `automation_delivery_targets` freezes each destination a personal automation copies its results to, one row per `target_type`. A `slack_agent_dm` row carries the selected Slack installation and linked Slack user; an `email` row carries the owner's account address as it stood when the automation was saved and no connector connection. A per-type `CHECK` keeps the two shapes from mixing. Avalon itself is never a row — every run already owns a work stream.
- `slack_unfurled_links` records which Slack message carries which work-stream link, plus a hash of the attachment posted on it, so a posted unfurl card is rewritten exactly when it would render differently. Slack reports a shared link only once, so a row that is not written as the card is posted can never be recovered — see [`WORKSTREAM_LINKS.md`](WORKSTREAM_LINKS.md).
- `activities` stores normalized metadata and an optional R2 payload reference. `target_user_ids_json` preserves explicit owner/mention routing separately from visibility, while `external_people_json` retains bounded provider identities and exact mention evidence for workspace-scoped resolution. Provider identity and dedupe constraints make at-least-once delivery safe.
- `resource_watches` records explicit direct relationships.
- `webhook_receipts` prevents replay of signed generic-webhook deliveries.
- `audit_events` records security- and side-effect-relevant actions without copying sensitive bodies.

## Invariants

1. A personal connection must have an owner; a workspace connection must not.
2. Passive viewing never creates `workstream_participants` rows.
3. A human authoring a message or elicitation answer is upserted as a participant in the same operation.
4. A personal activity is never promoted to workspace scope implicitly.
5. Repeated provider events, Queue deliveries, alarms, workflow steps, client messages, and tool calls converge on unique keys.
6. Canonical timestamps are UTC ISO-8601 strings. Every user and workspace retains a validated IANA timezone. Calendar intent separately retains its explicit IANA timezone; omitted automation timezones resolve in the order explicit trigger, personal user, then workspace.
7. R2 objects are addressed through opaque references; raw provider payloads do not enter Queue or Workflow inputs.

## Migration policy

Migration files are immutable after deployment. New schema changes receive a monotonically numbered SQL file. Local and hosted databases are migrated with Wrangler before code that depends on the new schema is deployed. Runtime request handlers never attempt broad schema migration.
